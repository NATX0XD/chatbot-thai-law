# พิมพ์เขียว: หลักการทำงานของแชตบอต และพรอมต์สำหรับสร้างบอทตัวใหม่จากชุดข้อมูลอื่น

เอกสารนี้มี 3 ส่วน
1. หลักการทำงานของบอทตัวนี้ (ถอดจากโค้ดจริง ไม่ใช่ทฤษฎี)
2. พรอมต์ที่ใช้จริง แบบถอดชื่อโดเมนออกเป็นตัวแปร
3. พรอมต์สั่งงาน (build prompt) สำหรับให้เอเจนต์สร้างบอทตัวใหม่จาก dataset คนละตัว

## ส่วนที่ 1 — หลักการทำงาน

### 1.1 หลักคิดหลัก

> **retriever เป็นคนตัดสินว่า "ตอบได้ไหม" ไม่ใช่ LLM**
> LLM มีหน้าที่เดียวคือ *เรียบเรียง* ตัวบทที่ค้นมาได้ ห้ามเติมความรู้ของตัวเอง
> และทุกอย่างที่ LLM เขียนออกมา ถูกตรวจซ้ำด้วยกฎ (ไม่ใช่ด้วย LLM) ก่อนส่งถึงผู้ใช้

เหตุผล: ในโดเมนที่ผิดแล้วเสียหาย (กฎหมาย การแพทย์ การเงิน นโยบายบริษัท) การ **ไม่ตอบ** ถูกกว่าการเดา
และโมเดลเป็นสิ่งที่ผิดที่จะถามว่า "ตัวเองรู้เรื่องนี้จริงไหม"

### 1.2 ท่อทั้งเส้น (`app/answer.py:answer_question`)

```
คำถาม
 │
 ├─ 0. smalltalk route ── ทักทาย/ถามว่าทำอะไรได้ ─> ตอบข้อความสำเร็จรูป (ไม่ค้น ไม่เรียก LLM)
 │
 ├─ 1. coverage rule (find_gap) ── คำถามอยู่ในหมวดที่คลัง "ไม่มี" ─> ปฏิเสธทันที
 │                                  (ก่อน retrieval เพราะพวกนี้ค้นแล้วได้คะแนน "สูง")
 │
 ├─ 2. retrieval  = BM25 + Dense ─ รวมอันดับด้วย RRF ─ boost เลขมาตรา ─ สำรองที่นั่งฝั่ง dense
 │      └─ gate: cosine สูงสุด < MIN_DENSE_SIM ─> ปฏิเสธ (ไม่เรียก LLM)
 │
 ├─ 3. LLM เขียนคำตอบ จากตัวบท top-k เท่านั้น (system prompt เข้มงวด + provider fallback chain)
 │
 ├─ 4. answer_beyond_corpus(คำตอบ) ── คำตอบไหลไปพูดเรื่องที่คลังไม่มี ─> ทิ้ง เปลี่ยนเป็นปฏิเสธ
 │
 ├─ 5. unsupported_laws(คำตอบ, citations) ── คำตอบอ้างกฎหมายที่ไม่ได้ป้อนให้ ─> ทิ้ง (hallucination)
 │
 └─ 6. tidy_for_chat ── ลอก markdown/วงเล็บเหลี่ยม/หัวข้อออก + ต่อท้าย disclaimer
```

### 1.3 ทำไมต้อง guard 4 ชั้น (แต่ละชั้นจับคนละความล้มเหลว)

| ชั้น | จับอะไร | ทำไมชั้นอื่นจับไม่ได้ |
|:---|:---|:---|
| 1 `find_gap` (กฎ keyword บนคำถาม) | คำถามที่ตัวบทจริงไม่อยู่ในคลัง | คะแนน **สูง** เพราะ retriever ไปเจอกฎหมายจริงที่หัวข้อใกล้กัน — score แยกไม่ออกตลอดกาล |
| 2 cosine gate | คำถามนอกโดเมนโดยสิ้นเชิง | กฎ keyword เขียนครอบไม่หมด |
| 3 `answer_beyond_corpus` (กฎบนคำตอบ) | คำถามถามเรื่องที่มี แต่คำตอบไหลไปเรื่องที่ไม่มี | ชั้น 1 ดูแค่คำถาม; ชั้น 5 ไม่ติดเพราะคำตอบไม่ได้อ้างชื่อกฎหมายผิด |
| 4 `unsupported_laws` (กฎบนคำตอบ) | โมเดลอ้างชื่อกฎหมายที่ไม่เคยถูกป้อน = แต่งขึ้น | prompt ห้ามแล้วยังทำ |

ไม่มีชั้นไหนถาม LLM ว่า "ควรตอบไหม" — ชั้น 3, 4 แค่ *อ่านสิ่งที่โมเดลเขียนเสร็จแล้ว*

**ตัวอย่างจริงที่ทำให้ต้องมีชั้น 4** ผู้ใช้ถามเรื่องขโมยของ ตอนนั้นคลังไม่มีประมวลอาญา
retriever คืน พ.ร.บ.ระบบการชำระเงิน ม.48 ที่ cosine 0.588 (เหนือ gate) โมเดลไม่สนใจ context
แล้วตอบจากความจำตัวเองว่า "ผิดฐานลักทรัพย์ ป.อาญา ม.335 โทษจำคุกไม่เกิน 5 ปี
(พ.ร.บ. ว่าด้วยการกระทำผิดเกี่ยวกับทรัพย์สิน พ.ศ. ...)" — ฉบับหลังไม่มีอยู่จริงบนโลก

### 1.4 การค้นคืน (`app/retriever.py`)

- **hybrid เพราะคำถามมาสองแบบ**
  - คนรู้ศัพท์: "ค่าชดเชย มาตรา 118" → BM25 แม่น / dense พลาด (embedding กลืนตัวเลข)
  - คนทั่วไป: "โดนไล่ออกกะทันหัน ได้เงินไหม" → dense ได้ / BM25 ไม่เจอเลย
- **RRF ใช้สำหรับ "จัดอันดับ" เท่านั้น** เพราะ BM25 score กับ cosine ไม่อยู่บนสเกลเดียวกัน
- **RRF ใช้เป็น guardrail ไม่ได้** RRF คิดจากอันดับล้วน — "สูตรทำต้มยำกุ้ง" ได้คะแนนสูงสุด 0.0164
  เท่ากับคำถามที่ตรงเป๊ะ ⇒ gate ต้องอ่าน **cosine ดิบ**
- **BM25 ห้ามอยู่ใน gate** วัดแล้ว: คำถามนอกเรื่องได้ BM25 ถึง 15.1 ขณะที่คำถามที่ตอบได้ต่ำสุด 12.6
- **สำรองที่นั่ง (`guarantee_top`)** RRF มีข้อเสียที่รู้กัน: chunk ที่ฝั่งหนึ่งให้อันดับ 1 แต่อีกฝั่งไม่ติด top-30
  ได้แค่ 1/61 แพ้ chunk กลางตารางสองฝั่ง (1/31 + 1/31) ⇒ จองที่นั่งให้ท็อปของ dense ไว้ 2 ที่
- **เลขมาตราในคำถาม = ข้อบังคับ ไม่ใช่คำใบ้** เจอ "มาตรา N" → บวกคะแนนตรง ๆ และ **ข้าม gate**
- **normalise เลขไทย→อารบิก ก่อนทุกเส้นทาง** ไม่งั้น "มาตรา ๑๑๘" กับ "มาตรา 118" ค้นได้คนละผล
- **ไม่ใช้ vector DB** 27k เวกเตอร์ × 1024 มิติ float16 = 56 MB โหลดเข้า RAM แล้ว matmul ครั้งเดียวจบ
  (mmap + chunk 4096 แถวเพื่อคุมหน่วยความจำ)

### 1.5 Query expansion (`app/query_expand.py`) — จุดที่ให้ผลคุ้มที่สุด

ตารางกฎ `ภาษาพูด → ศัพท์ทางการ` แล้ว **ต่อท้าย** คำถาม (ไม่แทนที่)

| คำถาม | ผลก่อน → หลัง |
|:---|:---|
| โดนไล่ออก ได้เงินไหม | cosine 0.63 → 0.77, top hit เปลี่ยนจาก พ.ร.บ.เงินเดือนข้าราชการ → คุ้มครองแรงงาน ม.118/119/122 |
| ลาพักร้อนกี่วัน | 0.61 → 0.78 |

ใช้ตารางกฎแทน LLM rewrite เพราะ ฟรี, ไม่เพิ่ม latency, deterministic, เทสต์ได้
บาง entry มี **context pattern** บังคับ (เช่น "กลางคืน" จะแปลว่าเวลาทวงหนี้ ก็ต่อเมื่อคำถามมีคำว่า หนี้/เจ้าหนี้)

### 1.6 ชั้น LLM (`app/llm.py`)

- ทุก provider พูด OpenAI protocol ⇒ SDK เดียว เปลี่ยน base_url เอา
- chain: Typhoon 30B → Typhoon 12B → Gemini (ต่อเมื่อมีคีย์)
- fallback ทำงานเมื่อ RateLimitError / APIStatusError / **ตอบกลับมาว่าง**
- ทุกตัวได้ system prompt เดียวกัน + ตัวบทชุดเดียวกัน + ผ่าน guard เดียวกัน
  ⇒ provider ตัวที่สองซื้อ **ความพร้อมใช้งาน** ไม่ใช่ **ความเห็นที่สองเรื่องกฎหมาย**

### 1.7 การปฏิเสธ (`app/refuse.py`) — ให้โมเดลเรียบเรียง แต่ไม่ให้ตัดสิน

ปัญหาเดิม: ข้อความปฏิเสธคงที่ก้อนเดียว เจอสองครั้งผู้ใช้เลิกอ่าน
ทางแก้: **กฎเป็นคนตัดสินว่าจะปฏิเสธ** แล้วส่ง verdict ให้โมเดลเรียบเรียงเป็นภาษาคน
แล้ว **ตรวจข้อความปฏิเสธนั้นอีกที** ถ้าเผลอมีเลขมาตรา / ตัวเลขเงิน-วัน-ร้อยละ / เอ่ยชื่อกฎหมายฉบับอื่น
→ ทิ้ง ใช้ข้อความคงที่แทน (น่าเบื่อแต่ผิดไม่ได้)

### 1.8 ฟอร์แมตสำหรับหน้าจอแชท

LINE แสดงข้อความธรรมดาเท่านั้น ⇒ prompt ห้าม markdown + มี `tidy_for_chat()` เป็นตาข่ายรับ
(prompt รุ่นแรกใช้โครง `[คำตอบสั้น 1-3 ประโยค]` แล้วโมเดลก๊อปวงเล็บเหลี่ยมออกมาด้วย)
LINE: reply token หมดอายุ ~30 วินาที แต่ RAG+LLM ใช้เวลากว่านั้นได้ ⇒ ตอบ 200 ทันที ประมวลผลใน background
ถ้า token หมดอายุก่อน สลับไปใช้ push API

### 1.9 การวัดผล (ส่วนที่ทำให้ทั้งหมดนี้ไม่ใช่การเดา)

| สคริปต์ | วัดอะไร |
|:---|:---|
| `ingest/calibrate.py` | การกระจาย cosine ของ 3 กลุ่มคำถาม (ตอบได้ / นอกโดเมน / ในโดเมนแต่ไม่มีตัวบท) → ใช้ตั้ง `MIN_DENSE_SIM` |
| `ingest/eval_retrieval.py` | hit@1/3/6, MRR@6 บนคำถามที่มีเฉลยระดับมาตรา |
| `ingest/tune_fusion.py` | grid search น้ำหนัก dense:bm25 |

ผลที่ใช้ตัดสินใจจริง: gate 0.54 (ตอบได้ 0.592–0.754 / นอกเรื่อง 0.331–0.496),
น้ำหนัก 3.0 : 0.25 (hit@1 60.7% เทียบ dense เดี่ยว 60.3%, BM25 เดี่ยว 44.0%)

## ส่วนที่ 2 — พรอมต์ที่ใช้จริง (แบบมีตัวแปร)

แทนค่าตัวแปร แล้วใช้ได้กับโดเมนอื่นทันที

| ตัวแปร | ของบอทนี้ | ตัวอย่างโดเมนอื่น |
|:---|:---|:---|
| `{ROLE}` | ผู้ช่วยให้ข้อมูลกฎหมายไทยสำหรับประชาชนทั่วไป | ผู้ช่วยตอบระเบียบ HR ของบริษัท |
| `{SOURCE_UNIT}` | ตัวบท (มาตรา) | ข้อ/หน้า/หัวข้อในคู่มือ |
| `{CITE_FORMAT}` | `(พ.ร.บ.คุ้มครองแรงงาน 2541 ม.118)` | `(ระเบียบบุคคล 2567 ข้อ 12)` |
| `{CHANNEL_RULES}` | ข้อห้าม markdown ของ LINE | ถ้าเป็นเว็บที่ render markdown ได้ ให้ตัดบล็อกนี้ทิ้ง |
| `{MAX_LINES}` | 12 | ตามหน้าจอ |

### 2.1 System prompt — ตอบคำถาม (`app/answer.py:SYSTEM_PROMPT`)

```
คุณคือ{ROLE} ตอบผ่าน{CHANNEL}

เนื้อหา
1. ตอบจาก{SOURCE_UNIT}ที่ให้มาเท่านั้น ห้ามใช้ความรู้อื่น
2. ทุกข้อความที่เป็นสาระ ต้องอ้างแหล่งในวงเล็บโค้ง เช่น {CITE_FORMAT} ใช้ชื่อย่อแบบนี้ ไม่ต้องเขียนชื่อเต็ม
3. ถ้า{SOURCE_UNIT}ไม่พอจะตอบ บอกตรง ๆ ว่าข้อมูลไม่พอ ห้ามเดา ห้ามแต่งเลข{SOURCE_UNIT}
4. อธิบายด้วยภาษาที่คนทั่วไปเข้าใจ ห้ามคัดลอก{SOURCE_UNIT}มาทั้งดุ้น
5. ถ้ามีตัวเลขสำคัญ เช่น จำนวนวัน จำนวนเงิน ให้ระบุเป็นเลขอารบิก

รูปแบบสำหรับหน้าจอแชท
- ย่อหน้าแรกคือคำตอบตรง ๆ 1-2 ประโยค ต้องอ่านจบแล้วได้คำตอบทันที
- เว้นบรรทัดว่าง แล้วอธิบายเหตุผลสั้น ๆ พร้อมอ้างแหล่ง
- ถ้ามีขั้นตอนที่ทำต่อได้ ให้ขึ้นบรรทัดใหม่แต่ละข้อ นำหน้าด้วย 1. 2. 3.
- ถ้ามีเงื่อนไขหลายกรณี ให้ขึ้นบรรทัดใหม่แต่ละกรณี นำหน้าด้วย •
- ความยาวรวมไม่เกิน {MAX_LINES} บรรทัด

ข้อห้ามเรื่องรูปแบบ
- ห้ามใส่วงเล็บเหลี่ยม [ ] ในคำตอบเด็ดขาด
- ห้ามใช้ ** __ ## ``` หรือสัญลักษณ์ markdown ใด ๆ
- ห้ามใส่หัวข้อกำกับ เช่น คำตอบ: หรือ คำอธิบาย:
- ห้ามขึ้นต้นด้วยการทวนคำถาม
- ห้ามพูดถึงตัวระบบ เช่น ข้อความถูกตัดทอน ผู้ใช้ไม่ต้องรู้เรื่องนี้

ข้อห้ามที่สำคัญที่สุด
ห้ามอ้างชื่อ{SOURCE_NAME}ที่ไม่ได้อยู่ใน{SOURCE_UNIT}ที่ให้มาเด็ดขาด แม้จะมั่นใจว่าจำได้ก็ตาม
ถ้า{SOURCE_UNIT}ที่ให้มาไม่ตรงกับคำถามเลย ให้ตอบเพียงว่าไม่มีข้อมูลพอ ห้ามตอบจากความรู้เดิม
```

**User prompt**
```
คำถามของผู้ใช้
{question}

{SOURCE_UNIT}ที่ค้นได้
[1] {citation_1}
{text_1}

[2] {citation_2}
{text_2}
...
```

### 2.2 System prompt — เรียบเรียงคำปฏิเสธ (`app/refuse.py:SYSTEM`)

```
คุณคือ{ROLE} ที่กำลังบอกผู้ใช้ว่าตอบคำถามนี้ไม่ได้

เขียนคำตอบสั้น ๆ 2-4 ประโยค ภาษาพูดที่สุภาพและเป็นธรรมชาติ เหมือนคนช่วยจริง ๆ ไม่ใช่ข้อความอัตโนมัติ

สิ่งที่ต้องมี
1. บอกว่าเรื่องนี้อยู่ใน{SOURCE_NAME}อะไร โดยเรียกชื่อกว้าง ๆ ตามที่ระบุให้ ไม่ต้องลงรายละเอียด
2. บอกตรง ๆ ว่าคลังข้อมูลของคุณไม่มีเนื้อหานั้น จึงไม่ตอบ เพราะไม่อยากเดา
3. ชี้ทางไปที่ที่ถามได้จริง ตามที่ระบุให้

ห้ามเด็ดขาด
- ห้ามตอบคำถามนั้นไม่ว่าบางส่วนหรือทั้งหมด
- ห้ามอ้างเลข{SOURCE_UNIT}
- เอ่ยชื่อ{SOURCE_NAME}ได้เฉพาะฉบับที่ระบุให้เท่านั้น ห้ามเอ่ยฉบับอื่น
- ห้ามบอกตัวเลข จำนวนเงิน จำนวนวัน หรือร้อยละ
- ห้ามคาดเดาว่าเนื้อหาน่าจะเขียนว่าอย่างไร
- ห้ามใช้ ** ## หรือสัญลักษณ์จัดรูปแบบ
- ห้ามขึ้นต้นด้วยคำว่า ขออภัย หรือ ขอโทษ
- แทนตัวเองว่า ผม และลงท้ายว่า ครับ เสมอ

เขียนให้ต่างกันไปตามคำถามที่ได้รับ อย่าใช้ประโยคเดิมซ้ำ
```

**User prompt**
```
คำถามของผู้ใช้
{question}

เรื่องนี้อยู่ในหมวด {topic}
เรียกชื่อแบบกว้าง ๆ ได้ว่า {code}
ที่ที่ผู้ใช้ควรไปถามต่อ
{where}
```

**ตัวกรองหลังโมเดลเขียนเสร็จ (บังคับมี)** — ผิดข้อใดข้อหนึ่ง = ทิ้ง ใช้ข้อความคงที่แทน
- ว่าง หรือยาวเกิน 700 ตัวอักษร
- มีเลข{SOURCE_UNIT} (`มาตรา\s*[๐-๙0-9]|ม\.\s*[๐-๙0-9]`)
- มีจำนวนเงิน/วัน/เดือน/ปี/% (`[๐-๙0-9][\d,\.]*\s*(บาท|วัน|เดือน|ปี|%)`) หรือคำว่า `ร้อยละ`
- เอ่ยชื่อแหล่งอื่นนอกจากฉบับที่อนุญาต

## ส่วนที่ 3 — พรอมต์สั่งสร้างบอทตัวใหม่จาก dataset คนละตัว

ก๊อปทั้งบล็อกไปวางให้เอเจนต์ (Claude / Codex / Antigravity) แล้วเติม 5 บรรทัดบนสุด

````
# งาน
สร้าง RAG chatbot ตอบคำถามจาก dataset ที่ระบุ โดยยึดสถาปัตยกรรมของ thai-law-bot
(hybrid retrieval + guard หลายชั้น + LLM เรียบเรียงอย่างเดียว)

# ตัวแปรของโปรเจกต์นี้
DOMAIN        = <โดเมน เช่น ระเบียบ HR ภายในบริษัท>
DATASET       = <ที่อยู่ไฟล์/HF dataset + ขนาด + ลิขสิทธิ์>
SOURCE_UNIT   = <หน่วยอ้างอิงที่เล็กที่สุด เช่น ข้อ / section / หน้า / QA pair>
CITE_FORMAT   = <หน้าตา citation ที่ต้องการ เช่น (ระเบียบบุคคล 2567 ข้อ 12)>
CHANNEL       = <LINE / เว็บ / Slack — กำหนดว่าห้าม markdown ไหม>
KNOWN_GAPS    = <หัวข้อที่ dataset นี้ "ไม่มี" และผู้ใช้จะถามแน่ ๆ>

# กฎเหล็ก 5 ข้อ (ห้ามละเมิด)
1. LLM ห้ามเป็นคนตัดสินว่าตอบได้หรือไม่ได้ — กฎและคะแนน retrieval ตัดสิน
2. LLM ตอบจาก context ที่ป้อนเท่านั้น ห้ามใช้ความรู้ในตัวโมเดล
3. ทุกคำตอบต้องมี citation ระดับ SOURCE_UNIT และต้องตรวจย้อนว่า citation นั้นมาจาก context จริง
4. ห้าม tune พารามิเตอร์ด้วยความรู้สึก ทุกค่า (threshold, น้ำหนัก fusion, top_k) ต้องมีสคริปต์วัดรองรับ
5. เส้นทางปฏิเสธห้ามเรียก LLM เพื่อขออนุญาต และข้อความปฏิเสธต้องถูกตรวจก่อนส่ง

# ขั้นตอน

## A. Ingest  (ingest/extract_*.py -> data/processed/corpus.jsonl)
- แตก dataset เป็น record ระดับ SOURCE_UNIT ฟิลด์: id, doc (ชื่อเอกสาร), section, part, text
- ตัด record ยาวเป็นหลาย part (part=0 คือท่อนเปิดของหน่วยนั้น)
- data/raw ห้ามแก้, data/processed คือของที่ใช้จริง, data/index สร้างใหม่ได้เสมอ
- พิมพ์สถิติออกมา: จำนวนเอกสาร จำนวน record ความยาวเฉลี่ย/สูงสุด

## B. Index  (ingest/build_index.py)
- ทุก chunk ต้อง embed แบบ "ชื่อเอกสาร + เลขหน่วย + \n + เนื้อหา"
  (หน่วยสั้น ๆ อย่าง "ปีบัญชีหมายถึงปีงบประมาณ" ไม่มีความหมายถ้าไม่มีชื่อเอกสารนำหน้า)
- Dense: embedding model ที่รองรับภาษาของ dataset (BGE-M3 ถ้าเป็นไทย), normalize, เก็บ float16 เป็น .npy
- Sparse: BM25 บน tokenizer ที่ vendored ไว้ในโปรเจกต์ (ห้ามพึ่ง lib ภายนอกที่อัปเกรดแล้ว token เปลี่ยน)
- เช็ค len(vectors) == len(corpus) ตอนโหลด ถ้าไม่ตรง raise ทันที
  (index เก่ากับ corpus ใหม่จะไม่ error เอง มันแค่ตอบผิดเงียบ ๆ)

## C. Retrieval  (app/retriever.py)
- normalise ตัวเลข/รูปแบบก่อน ทุกเส้นทาง
- query expansion ด้วยตารางกฎ ภาษาพูด -> ศัพท์ในเอกสาร (ต่อท้าย ไม่แทนที่)
  entry ไหนมีคำกำกวมให้ใส่ context pattern บังคับ
- ค้น dense top-30 + BM25 top-30 รวมด้วย RRF (k=60) ถ่วงน้ำหนัก
- จองที่นั่ง top-2 ของ dense ไว้เสมอ (กัน RRF ฝังผลอันดับ 1 ของฝั่งเดียว)
- ถ้าผู้ใช้พิมพ์เลข SOURCE_UNIT มาตรง ๆ ให้ boost และข้าม gate
- in_scope ตัดสินจาก **cosine ดิบ** เท่านั้น ห้ามใช้คะแนน RRF และห้ามใช้ BM25

## D. Guards  (app/coverage.py, app/verify.py)
- coverage.py: regex ของ KNOWN_GAPS 2 ชุด
    find_gap(question)        -> เช็คก่อน retrieval
    answer_beyond_corpus(ans) -> เช็คคำตอบที่โมเดลเขียนเสร็จแล้ว
  ข้อความปฏิเสธต้องบอก 3 อย่าง: เรื่องนี้อยู่ในเอกสารอะไร / คลังไม่มี จึงไม่เดา / ให้ไปถามที่ไหนแทน
- verify.py: ดึงชื่อเอกสารทุกชื่อที่ปรากฏในคำตอบ normalise แล้วเทียบกับชื่อใน citations ที่ป้อนไป
  ถ้ามีชื่อที่ไม่ได้ป้อน = แต่งขึ้น -> บล็อกทั้งคำตอบ
  ระวัง 3 เคสที่เคยทำให้ "คำตอบถูกโดนบล็อก":
    - self-reference ("ตามระเบียบนี้", "ฉบับดังกล่าว") ต้องข้าม
    - ชื่อย่อที่คนใช้จริงฝังอยู่กลางชื่อทางการ -> เทียบแบบ containment ไม่ใช่ prefix
    - เรียกผิดประเภทเอกสาร (เรียกประมวลว่า พ.ร.บ.) = เรียกผิดชื่อ ไม่ใช่แต่งขึ้น

## E. LLM layer  (app/llm.py, app/answer.py)
- ใช้ OpenAI-compatible SDK ตัวเดียว ตั้ง chain หลาย provider ไว้ fallback
- fallback เมื่อ: RateLimitError / APIStatusError / คืนข้อความว่าง
- temperature 0.2, max_tokens ~1200
- ถ้าทุก provider ล่ม ห้ามคืนข้อความว่าง ให้คืน "รายการ SOURCE_UNIT ที่ค้นเจอ" แทน
  (retrieval ยังทำงาน ผู้ใช้ควรได้อะไรกลับไป)
- ต่อ disclaimer ทุกคำตอบ ระบุว่าคลังข้อมูลปรับปรุงถึงเมื่อไหร่

## F. Smalltalk
- route "สวัสดี" / "ทำอะไรได้บ้าง" ออกก่อน retrieval
  (วัดจริงแล้วได้ cosine 0.445 และ 0.512 = ตกใต้ gate แล้วโดนตอบด้วยข้อความปฏิเสธยาวเหยียด)
- ข้อความ capability ต้องบอกทั้ง "ตอบอะไรได้" และ "ตอบอะไรไม่ได้"

## G. วัดผล (ต้องมีก่อนเรียกว่าเสร็จ)
- calibrate.py: เตรียมคำถาม 3 กลุ่ม กลุ่มละ >=10 ข้อ
    (1) ตอบได้จริง (2) นอกโดเมนสิ้นเชิง (3) ในโดเมนแต่เนื้อหาไม่อยู่ในคลัง  <- กลุ่มนี้สำคัญที่สุด
  พิมพ์ min/max/mean cosine ของแต่ละกลุ่ม แล้วเลือก threshold ที่อยู่ในช่องว่างระหว่างกลุ่ม 1 กับ 2
  ถ้ากลุ่ม 3 ทับกลุ่ม 1 (มันจะทับ) -> นั่นคือเหตุผลที่ต้องมี coverage rule ห้ามแก้ด้วยการขยับ threshold
- eval_retrieval.py: hit@1/3/6 + MRR@6 เทียบ 3 ค่า: hybrid / dense เดี่ยว / BM25 เดี่ยว
  ถ้า hybrid ไม่ชนะ dense เดี่ยว ให้ grid search น้ำหนักใหม่ อย่าปล่อยผ่าน
- tests/: อย่างน้อย
    คำถามภาษาพูดค้นเจอหน่วยที่ถูก / เลขหน่วยที่ผู้ใช้พิมพ์ถูก honor /
    เส้นทางปฏิเสธไม่เรียก LLM เลย / คำตอบมี citation เสมอ /
    LLM ล่มแล้วยังคืนเนื้อหาให้ / guard จับ citation ปลอมได้

# สิ่งที่ต้องรายงานกลับ
1. จำนวน record ในคลัง + สิ่งที่ dataset นี้ "ไม่มี" (ทำให้เป็น KNOWN_GAPS)
2. ค่า threshold ที่เลือก พร้อมตารางคะแนน 3 กลุ่มที่ใช้ตัดสิน
3. ตาราง hit@k เทียบ 3 วิธีค้น
4. รายการ guard ที่ติดตั้ง + เคสที่แต่ละตัวจับได้

## ภาคผนวก — กับดักที่เสียเวลาที่สุด (เจอจริงในโปรเจกต์นี้)

ทั้งสามข้อ **ไม่มีอาการฟ้อง** ระบบทำงานปกติแต่ให้ผลผิด

1. **encode ทีละข้อความบน MPS ให้เวกเตอร์ผิด** cosine เทียบกับ CPU เหลือ 0.30 ในบางคำถาม
   แต่ encode เป็น batch ได้ 1.0000 พอดี ⇒ ดัชนีไม่เสีย (สร้างด้วย batch 16) แต่ฝั่ง query พังเงียบ ๆ
   **แก้: บังคับ encode query บน CPU และต้องมีเทสต์ parity เทียบ 300 chunk สุ่ม**
2. **RRF ฝังคำตอบที่ถูกที่สุดไว้ท้ายแถว** ⇒ ต้องสำรองที่นั่งให้ท็อปของแต่ละ retriever
3. **คะแนน RRF ใช้เป็น guardrail ไม่ได้เลย** ⇒ gate ต้องอ่าน cosine ดิบ
4. **index/corpus mismatch** สร้าง corpus ใหม่แต่ลืม build index ⇒ ไฟล์โหลดผ่าน ระบบตอบได้
   แต่ตอบจากคลังเก่า ⇒ ต้อง raise ตอนโหลดเมื่อจำนวนไม่ตรง
5. **embedding provider คนละเจ้าที่ชื่อโมเดลเดียวกัน ไม่พอ** ต้องวัด cosine parity เทียบกับโมเดลที่สร้าง index
   (ของโปรเจกต์นี้วัดได้ 0.999999 ถึงยอมใช้)
