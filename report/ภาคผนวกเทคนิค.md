### 1.2 `data/index/vectors.npy` — 55.7 MB

เมทริกซ์ NumPy รูปร่าง `(27203, 1024)` ชนิด `float16`
แถวที่ *i* คือเวกเตอร์ของ `corpus.jsonl` บรรทัดที่ *i* — ลำดับผูกกันแบบตำแหน่งต่อตำแหน่ง
ถ้าลำดับหลุด ระบบจะตอบผิดโดยไม่มีอาการฟ้อง จึงมีการตรวจตอนโหลดว่าจำนวนแถวเท่ากับจำนวนบรรทัดเสมอ

ทุกเวกเตอร์ถูกทำ L2 normalisation ตอนสร้าง แปลว่าความยาวของทุกเวกเตอร์เท่ากับ 1 พอดี
ผลคือ **cosine similarity ลดรูปเหลือ dot product** ตัดการหารด้วยความยาวออกได้ทั้งหมด

$$\cos(\vec{q},\vec{d}) = \frac{\vec{q}\cdot\vec{d}}{\|\vec{q}\|\|\vec{d}\|} = \vec{q}\cdot\vec{d} \quad\text{เมื่อ } \|\vec{q}\|=\|\vec{d}\|=1$$

`float16` ให้ความละเอียดราว 3 หลักนัยสำคัญ ซึ่งพอสำหรับ cosine ที่เราตัดสินที่ทศนิยม 2 ตำแหน่ง
และประหยัดครึ่งหนึ่งเทียบกับ `float32` (55.7 MB แทน 111 MB)

## 2. BM25 — สูตรเต็มและตัวอย่างคำนวณจริง

### 2.1 สูตร

$$\text{score}(q,d)=\sum_{t \in q}\ \text{idf}(t)\cdot\frac{f(t,d)\cdot(k_1+1)}{f(t,d)+k_1\left(1-b+b\cdot\dfrac{|d|}{\text{avgdl}}\right)}$$

| สัญลักษณ์ | ความหมาย | ค่าในระบบนี้ |
|:---|:---|:---|
| $f(t,d)$ | จำนวนครั้งที่คำ $t$ โผล่ในเอกสาร $d$ | จาก `tf` |
| $\|d\|$ | ความยาวเอกสาร $d$ นับเป็นโทเคน | |
| avgdl | ความยาวเฉลี่ยของทุกเอกสาร | 91.11 โทเคน |
| $k_1$ | คุมความอิ่มตัวของความถี่ | 1.5 |
| $b$ | คุมการหักตามความยาว 0 = ไม่หักเลย 1 = หักเต็ม | 0.75 |

$$\text{idf}(t)=\ln\left(\frac{N-n(t)+0.5}{n(t)+0.5}+1\right)$$

โดย $N$ = 27,203 และ $n(t)$ = จำนวนเอกสารที่มีคำ $t$

**ความหมายของแต่ละส่วน**

- **idf** คำที่โผล่ในเอกสารน้อยได้ค่าสูง คำที่โผล่ทุกที่ได้ค่าต่ำ
- **ตัวเศษ $f\cdot(k_1+1)$ กับตัวส่วนที่มี $f$** ทำให้คะแนนอิ่มตัว —
  เจอคำ 20 ครั้งไม่ได้คะแนนเป็น 4 เท่าของเจอ 5 ครั้ง
- **$1-b+b\cdot|d|/\text{avgdl}$** เอกสารยาวกว่าค่าเฉลี่ยได้ตัวหารมากขึ้น คะแนนจึงถูกหักลง

### 2.2 การคำนวณล่วงหน้าที่ทำให้เร็วขึ้น

ส่วน $k_1(1-b+b|d|/\text{avgdl})$ ไม่ขึ้นกับคำถามเลย ขึ้นกับเอกสารอย่างเดียว
จึงคำนวณไว้ล่วงหน้าทั้ง 27,203 ค่าตั้งแต่ตอนสร้างดัชนี เก็บเป็นอาเรย์ `norm`

สูตรตอนใช้งานจึงเหลือแค่

```
score += idf[t] * f * (k1 + 1) / (f + norm[doc])
```

### 2.3 ตัวอย่างคำนวณจริง

คำถาม `โดนไล่ออก ได้เงินไหม` หลังเติมศัพท์กฎหมายกลายเป็น
`โดนไล่ออก ได้เงินไหม การเลิกจ้าง ค่าชดเชย`

ตัดคำได้ 7 โทเคน ทุกตัวอยู่ในคลังคำ

| โทเคน | idf | อยู่ในกี่เอกสาร |
|:---|---:|---:|
| `โดน` | 6.860 | 28 |
| `ไล่ออก` | 5.072 | 169 |
| `ได้เงิน` | 7.470 | 15 |
| `ไหม` | 8.506 | 5 |
| `การ` | 1.931 | 16,346 |
| `เลิกจ้าง` | 5.898 | 74 |
| `ค่าชดเชย` | 6.533 | 39 |

เห็นชัดว่า `การ` โผล่ใน 16,346 เอกสารจาก 27,203 จึงได้ idf แค่ 1.931
ขณะที่ `ไหม` โผล่แค่ 5 เอกสารได้ 8.506

**คิดคะแนนของเอกสารที่ได้ที่ 1 ฝั่ง BM25** — พ.ร.บ.คุ้มครองแรงงาน 2541 มาตรา 121
(หมายเลขเอกสาร 12607, `norm` = 2.4618)

| โทเคน | $f$ | idf | คะแนน |
|:---|---:|---:|---:|
| `การ` | 4 | 1.931 | $1.931 \times \frac{4 \times 2.5}{4+2.4618}$ = 2.989 |
| `เลิกจ้าง` | 6 | 5.898 | $5.898 \times \frac{6 \times 2.5}{6+2.4618}$ = 10.454 |
| `ค่าชดเชย` | 3 | 6.533 | $6.533 \times \frac{3 \times 2.5}{3+2.4618}$ = 8.971 |
| **รวม** | | | **22.415** |

อีก 4 โทเคน (`โดน`, `ไล่ออก`, `ได้เงิน`, `ไหม`) ไม่ปรากฏในมาตรานี้เลย จึงไม่ได้คะแนน

**22.415 ตรงกับค่า `max_bm25` ที่ระบบจริงคืนกลับมาพอดี** —
เรียก `/search?q=โดนไล่ออก ได้เงินไหม` แล้วได้ `max_bm25: 22.415`
การคำนวณมือกับระบบจริงจึงตรงกันทุกทศนิยม

### 2.4 จุดที่ต้องระวังตอนเขียนตัวคำนวณเอง

ตัวเดิม (`rank_bm25`) วนลูปตามรายการโทเคน**ตามที่ได้มา** ไม่ได้รวมคำซ้ำ
ถ้าคำถามมีคำเดิม 2 ครั้ง คำนั้นจะถูกคิดคะแนน 2 รอบ

ตัวที่เขียนใหม่รอบแรกเผลอรวมคำซ้ำให้เหลือครั้งเดียว ซึ่งดูสมเหตุสมผลกว่า
แต่ทำให้อันดับเปลี่ยนจากที่จูนน้ำหนักไว้ทั้งหมด — โค้ดจึงมีคอมเมนต์กำกับไว้ว่า
**ตั้งใจไม่รวมคำซ้ำ** เพื่อไม่ให้ใครมาแก้ให้ "ถูกต้อง" ในภายหลัง

## 3. การตัดคำภาษาไทย

ใช้ newmm ของ PyThaiNLP (Apache-2.0) ที่ยกโค้ดมาไว้ในโปรเจกต์ ทำงาน 3 ชั้น

### ชั้นที่ 1 — TCC หาขอบที่ห้ามตัด

TCC ย่อจาก Thai Character Cluster คือกลุ่มอักขระที่แยกจากกันไม่ได้
เช่น `เก` ต้องอยู่ด้วยกันเพราะสระเอต้องมีพยัญชนะตาม `กิ` ก็เช่นกัน

ชั้นนี้ทำเครื่องหมายไว้ว่าตำแหน่งไหน**ห้าม**ตัด ก่อนจะเริ่มหาคำจริง ๆ
ทำให้ไม่มีทางได้ผลลัพธ์ที่ตัดกลางสระหรือกลางวรรณยุกต์

### ชั้นที่ 2 — trie หาคำที่เป็นไปได้ทั้งหมด

trie คือโครงสร้างต้นไม้ที่เก็บคำโดยใช้ตัวอักษรร่วมกัน คำที่ขึ้นต้นเหมือนกันใช้กิ่งเดียวกัน
ทำให้ถามได้เร็วมากว่า "จากตำแหน่งนี้ มีคำอะไรในพจนานุกรมที่เริ่มตรงนี้บ้าง"

พจนานุกรมที่ใช้มี **62,074 คำ**

### ชั้นที่ 3 — เลือกทางที่ตัดได้จำนวนคำน้อยที่สุด

ผลจากชั้นที่ 2 คือกราฟ — จากตำแหน่ง 0 ไปได้หลายที่ แต่ละที่ไปต่อได้อีกหลายที่
งานที่เหลือคือหาเส้นทางจากต้นประโยคถึงท้ายประโยคที่ผ่านโหนดน้อยที่สุด
ซึ่งก็คือการตัดที่ได้จำนวนคำน้อยที่สุด ใช้การค้นแบบกว้างก่อน (BFS)

**กันระเบิด** ถ้ากราฟโตเกิน 50 โหนดจะตัดจบแล้วเลือกทางที่ดีที่สุดเท่าที่มี
เพราะจำนวนเส้นทางที่เป็นไปได้โตแบบเอ็กซ์โพเนนเชียลตามความยาวข้อความ
และมีโหมดปลอดภัยที่มองทีละหน้าต่าง 120 ตัวอักษรสำหรับข้อความยาวมาก

### ทำไมต้องยกโค้ดมา ไม่ import ตรง ๆ

สั่ง `import pythainlp` เฉย ๆ กินหน่วยความจำ 266 MB เพราะไฟล์เริ่มต้นของแพ็กเกจ

**และมีเหตุผลที่สำคัญกว่าเรื่องหน่วยความจำ** — ดัชนี BM25 สร้างด้วยตัวตัดคำตัวไหน

## 4. การค้นแบบ Dense

### 4.1 ตอนสร้างดัชนี

```python
text = f"{rec['act']} มาตรา {rec['section']}\n{rec['text']}"
```

ทุกชิ้นถูกเติมชื่อกฎหมายและเลขมาตรานำหน้าก่อนแปลงเป็นเวกเตอร์
แล้วเข้ารหัสด้วย BGE-M3 ทีละ 16 ชิ้น เปิด normalisation แล้วบันทึกเป็น `float16`

### 4.2 ตอนค้น

```python
q = embedder.encode(query)                      # (1024,) float32, ยาว 1
sims = np.empty(27203, dtype=np.float32)
for i in range(0, 27203, 4096):
    block = np.asarray(vectors[i:i+4096], dtype=np.float32)
    sims[i:i+len(block)] = block @ q
top = np.argpartition(-sims, k-1)[:k]
order = top[np.argsort(-sims[top])]
```

สามจุดที่ตั้งใจ

1. **`mmap_mode="r"`** ตอนโหลด — ไฟล์ไม่ถูกอ่านเข้าหน่วยความจำทั้งก้อน
   ระบบปฏิบัติการจะดึงหน้าที่ต้องใช้เข้ามาตอนที่การคูณเดินไปถึง และขับออกได้ถ้าหน่วยความจำตึง
   ซึ่งอาเรย์ธรรมดาทำไม่ได้
2. **คูณทีละ 4,096 แถว** — NumPy ไม่มีทางลัด BLAS สำหรับ `float16`
   ต้องแปลงเป็น `float32` ก่อน ถ้าแปลงทั้งก้อนจะกิน 111 MB
   หน้าต่าง 4,096 แถวกินแค่ 16 MB และเพราะมันพอดีแคชซีพียู จึงไม่ช้ากว่าการแปลงทีเดียว
3. **`argpartition` ก่อน `argsort`** — เราต้องการแค่ 30 อันดับแรกจาก 27,203
   `argpartition` แยก 30 ตัวบนออกมาโดยไม่เรียงทั้งอาเรย์ ($O(n)$ แทน $O(n\log n)$)
   แล้วค่อยเรียงเฉพาะ 30 ตัวนั้น

### 4.3 กับดักที่เจอจริง: MPS ให้เวกเตอร์ผิดเงียบ ๆ

## 6. การรวมอันดับ

### 6.1 สูตร

$$\text{RRF}(d)=\sum_{r \in \{\text{dense},\text{bm25}\}} \frac{w_r}{k + \text{rank}_r(d) + 1}$$

| ค่า | ตัวเลข | ที่มา |
|:---|---:|:---|
| $k$ | 60 | ค่ามาตรฐานในงานต้นฉบับของ RRF |
| $w_{\text{dense}}$ | 2.0 | ไล่ลองทั้งกริดด้วย `ingest/tune_fusion.py` |
| $w_{\text{bm25}}$ | 0.5 | เช่นกัน |
| จำนวนที่ดึงมาต่อฝั่ง | 30 | |
| จำนวนที่ส่งให้โมเดล | 6 | |

อันดับนับจาก 0 จึงบวก 1 ในตัวส่วน อันดับแรกได้ $w/61$

**ทำไมต้องรวมด้วยอันดับ ไม่ใช่คะแนน** คะแนน BM25 ในตัวอย่างข้อ 2.3 อยู่ที่ 22.415
ส่วน cosine อยู่ที่ 0.6812 บวกกันตรง ๆ แปลว่า BM25 กลบ cosine หมด
และการปรับสเกลให้เทียบกันได้ต้องรู้ช่วงของทั้งสองฝั่งล่วงหน้า ซึ่งเปลี่ยนไปตามคำถาม
RRF ไม่ต้องการอะไรแบบนั้นเลย

### 6.2 ตัวอย่างจริง — ตรวจเลขได้ทุกตัว

คำถาม `โดนไล่ออก ได้เงินไหม` เรียกผ่าน `/search`

| มาตรา | อันดับ dense | cosine | อันดับ bm25 | คะแนน bm25 | RRF ที่คำนวณ | RRF ที่ระบบคืน |
|:---|---:|---:|---:|---:|---:|---:|
| คุ้มครองแรงงาน ม.119 | 2 | 0.6538 | 2 | 17.58 | $\frac{2.0}{63}+\frac{0.5}{63}$ = 0.03968 | 0.03970 |
| ศาลแรงงาน ม.49 | 3 | 0.6515 | 1 | 19.97 | $\frac{2.0}{64}+\frac{0.5}{62}$ = 0.03932 | 0.03930 |
| คุ้มครองแรงงาน ม.122 | 7 | 0.6338 | 3 | 15.62 | $\frac{2.0}{68}+\frac{0.5}{64}$ = 0.03722 | 0.03720 |
| คุ้มครองแรงงาน ม.121 | 11 | 0.6198 | 0 | 22.41 | $\frac{2.0}{72}+\frac{0.5}{61}$ = 0.03598 | 0.03600 |
| **คุ้มครองแรงงาน ม.118** | **0** | **0.6812** | ไม่ติด | 0.00 | $\frac{2.0}{61}$ = 0.03279 | 0.03280 |
| คุ้มครองแรงงาน ม.135 | 1 | 0.6580 | ไม่ติด | 0.00 | $\frac{2.0}{62}$ = 0.03226 | 0.03230 |

**สังเกตแถวที่ 5** ม.118 คือมาตราที่ระบุอัตราค่าชดเชยจริง ได้ cosine สูงสุดของทั้งชุด (0.6812)
เป็นอันดับ 1 ฝั่ง dense แต่ **BM25 ไม่ติด 30 อันดับแรกเลย** เพราะไม่มีคำว่า
`โดน` `ไล่ออก` `ได้เงิน` `ไหม` อยู่ในมาตรานั้น

มันจึงได้แต้มจากฝั่งเดียว 0.0328 แพ้มาตราข้างเคียงที่กลาง ๆ ทั้งสองฝั่ง

**ถ้าใช้น้ำหนัก 1:1 จะเป็นยังไง** ม.118 จะได้ $1/61 = 0.0164$
ขณะที่ ม.119 ได้ $1/63+1/63 = 0.0317$ — คือ **ประมาณครึ่งเดียว**
แปลว่าทุกชิ้นที่ติดทั้งสองรายการจะแซงมันหมด ซึ่งตรงกับอาการที่เจอตอนแรกว่า
มาตราที่ตอบคำถามได้ตรงที่สุดหลุด 10 อันดับแรก

น้ำหนัก 2:1 แก้เคสนี้ได้ **โดยที่ที่นั่งสำรองยังไม่ต้องทำงานเลย** ในคำถามนี้ —
ม.118 กับ ม.135 ติด 6 อันดับแรกด้วยแต้มของตัวเองอยู่แล้ว
ที่นั่งสำรองคือตาข่ายชั้นที่สองสำหรับคำถามที่น้ำหนักอย่างเดียวยังไม่พอ

### 6.4 การดันเลขมาตราที่ผู้ใช้ระบุ

ถ้าคำถามมีรูปแบบ `มาตรา\s*(\d+(?:/\d+)?)` ทุกชิ้นที่มีเลขมาตราตรงกันจะได้แต้มบวก

| กรณี | แต้มที่บวก |
|:---|---:|
| ชิ้นแรกของมาตรานั้น (`part == 0`) | +0.5 |
| ชิ้นถัด ๆ ไป | +0.4 |

+0.5 มากกว่าแต้ม RRF สูงสุดที่เป็นไปได้ (2.5/61 ≈ 0.041) ราว 12 เท่า
เป็นการบังคับให้ขึ้นบนสุด ไม่ใช่แค่ช่วยดัน

ชิ้นแรกได้มากกว่าเพราะมันคือย่อหน้าที่เปิดกฎเกณฑ์ ซึ่งเป็นสิ่งที่คนถามหาเลขมาตราต้องการอ่าน

และการมีเลขมาตราในคำถามยัง **ข้ามด่านที่ 2** ด้วย (ดูข้อ 7.2)

### 7.2 ด่านที่ 2 — เกณฑ์ cosine

### 7.3 ด่านที่ 3 — ตรวจชื่อกฎหมายในคำตอบ

รูปแบบที่ใช้จับชื่อกฎหมายในคำตอบ

```python
LAW_MENTION = (ประมวลรัษฎากร
             | ประมวลกฎหมาย[ก-๙]+(?:และ[ก-๙]+)?
             | พระราชบัญญัติ...  | พระราชกำหนด...
             | พ.ร.บ....         | พ.ร.ก....)
```

หลังจับได้แล้ว **ทำให้ชื่ออยู่ในรูปเทียบกันได้** ก่อนเทียบ

| ขั้น | ทำอะไร |
|:---|:---|
| ตัดสิ่งรบกวน | `พ.ศ. 2541`, `มาตรา 118`, `ม.9`, `(ฉบับ Update ...)`, วงเล็บ, ช่องว่าง, เครื่องหมายวรรคตอน |
| ย่อรูปแบบ | `พระราชบัญญัติ` → ตัดทิ้ง, `ประมวลกฎหมาย` → `ประมวล` |
| เทียบ | ชื่อในคำตอบกับชื่อที่ส่งให้โมเดล ตรงกันที่ 12 ตัวอักษรแรกฝั่งใดฝั่งหนึ่งถือว่าผ่าน |

เทียบแบบ prefix สองทาง เพราะโมเดลอาจย่อ `พระราชบัญญัติคุ้มครองแรงงาน พ.ศ. 2541`
เหลือ `พ.ร.บ.คุ้มครองแรงงาน` หรืออาจเอ่ยแค่คำต้น ๆ ของชื่อที่ยาวมาก

**ปัญหาที่แก้ยากที่สุดคือขอบท้ายของชื่อ**

```
"ตาม พ.ร.บ.การทวงถามหนี้ 2558 ม.9 และประมวลกฎหมายแพ่งและพาณิชย์"
```

รูปแบบที่ให้กวาดคำต่อท้ายได้ 6 คำ จะกลืน `และประมวลกฎหมายแพ่งและพาณิชย์`
เข้ามาเป็นส่วนหนึ่งของชื่อเดียวกัน แล้วปล่อยผ่านเพราะขึ้นต้นด้วยชื่อจริง —
ชื่อกฎหมายปลอมจึงซ่อนอยู่ในชื่อจริงได้

แก้โดยหยุดชื่อที่คำเชื่อม

```python
STOP = r"(?!และ|หรือ|ตาม|กับ|ซึ่ง|โดย|เพื่อ|แต่|จึง|ที่|ใน|มาตรา|ม\.)"
```

**เคสจริงที่ทำให้ต้องมีด่านนี้** ผู้ใช้ถามเรื่องเพื่อนขโมยของ ระบบคืน
พ.ร.บ.ระบบการชำระเงิน ม.48 ที่ cosine 0.588 (เหนือเกณฑ์ แต่ไม่เกี่ยว)
โมเดลไม่สนใจตัวบทที่ให้ แล้วตอบว่า

```
"มีความผิดฐานลักทรัพย์ตามประมวลกฎหมายอาญา มาตรา 335 ... โทษจำคุกไม่เกิน 5 ปี
 (พ.ร.บ. ว่าด้วยการกระทำผิดเกี่ยวกับทรัพย์สิน พ.ศ. ...)"
```

ประมวลกฎหมายอาญาไม่อยู่ในคลัง และ พ.ร.บ. ตัวที่สองไม่มีอยู่จริง

**สิ่งที่ด่านนี้จับไม่ได้** ถ้าโมเดลอ้างกฎหมายที่เราส่งให้จริง แต่สรุปความหมายผิด
ด่านนี้ปล่อยผ่านทั้งหมด เพราะมันตรวจแค่ว่า *ชื่อ* ถูกต้อง ไม่ได้ตรวจว่า *เนื้อหา* ถูกต้อง

### 8.1 คำสั่งระบบ ฉบับเต็ม

```

- ถ้ามีขั้นตอนที่ทำต่อได้ ให้ขึ้นบรรทัดใหม่แต่ละข้อ นำหน้าด้วย 1. 2. 3.
- ถ้ามีเงื่อนไขหลายกรณี เช่น อายุงานต่างกันได้เงินต่างกัน ให้ขึ้นบรรทัดใหม่แต่ละกรณี นำหน้าด้วย •

## 12. ฝั่ง LINE

### 12.1 ตรวจลายเซ็น

```python
digest = hmac.new(channel_secret.encode(), body, hashlib.sha256).digest()
hmac.compare_digest(base64.b64encode(digest).decode(), x_line_signature)
```

`compare_digest` ไม่ใช่ `==` เพราะการเทียบสตริงทั่วไปหยุดทันทีที่เจอตัวต่าง
ทำให้เวลาที่ใช้บอกใบ้ได้ว่าเดาถูกไปกี่ตัว

### 12.2 ลำดับการตอบ

```
LINE ─POST /webhook─> ตรวจลายเซ็น ─> คืน 200 ทันที
                                      └─> งานเบื้องหลัง
                                            ├─ แสดงตัวบ่งชี้กำลังพิมพ์
                                            ├─ ตอบคำถาม (2-15 วินาที)
                                            ├─ reply ด้วยบัตรผ่าน
                                            └─ ถ้า reply ไม่สำเร็จ → push
```

บัตรผ่านสำหรับตอบกลับมีอายุราว 30 วินาที ส่วน push ไม่ต้องใช้บัตรผ่านแต่นับโควตา
จึงใช้ reply ก่อนเสมอ

### 12.3 กติกาในกลุ่ม

LINE ส่งทุกข้อความในกลุ่มมาให้บอต ถ้าตอบหมดจะใช้งานไม่ได้ บอตจึงตอบเฉพาะเมื่อ

1. ถูก @ ถึง — ดูจาก `isSelf` ในข้อมูลที่ LINE ส่งมา หรือเทียบกับรหัสผู้ใช้ของบอตเอง
2. ข้อความขึ้นต้นด้วย `กฎหมาย` `บอท` หรือ `bot`

การตอบในกลุ่มต้องส่งไปที่ `groupId` ไม่ใช่ `userId` ของคนถาม
ไม่งั้นคำตอบจะไปโผล่ในแชตส่วนตัวของคนถามแทนที่จะกลับเข้ากลุ่ม

### 12.4 คำตอบ 2 ข้อความ

ส่งทั้งข้อความธรรมดาและการ์ด เพราะทำหน้าที่คนละอย่าง —
ข้อความธรรมดาก็อปได้ ค้นได้ และแสดงผลได้บนทุกเวอร์ชัน
ส่วนการ์ดแยกมาตราออกจากเนื้อความให้ตรวจได้ในพริบตา

ข้อจำกัดของการ์ด — 10 ใบต่อหนึ่งชุด, 50 KB ต่อข้อความ, ใส่ตัวหนาในกล่องข้อความไม่ได้
การ์ดแสดงมาตราสูงสุด 3 มาตรา ที่เหลือสรุปเป็น "และอีก N มาตรา"

### 12.5 เมนูล่างจอ

รูป 2500 × 843 พิกเซล แบ่ง 3 ช่องเท่า ๆ กัน

| ช่อง | พิกัด | สิ่งที่เกิด |
|:---|:---|:---|
| ถามกฎหมาย | x 0–833 | ส่งข้อความ `ถามกฎหมาย` |
| ตัวอย่างคำถาม | x 833–1667 | ส่งข้อความ `ตัวอย่างคำถาม` |
| เปิดเว็บแชท | x 1667–2500 | เปิดที่อยู่เว็บ |

สองช่องแรกส่งข้อความดิบเข้าระบบ ซึ่งของเดิมจะถูกเอาไปค้นคืนแล้วปฏิเสธ
จึงต้องเพิ่มเส้นทางตอบสำเร็จรูปให้ทั้งสองข้อความ **และตอบคนละอย่าง** —
สองปุ่มที่ตอบเหมือนกันคือปุ่มหลอกหนึ่งปุ่ม

## 13. หน่วยความจำ วัดทีละขั้น

วัดด้วย `resource.getrusage(RUSAGE_SELF).ru_maxrss` ในคอนเทนเนอร์ที่จำกัดไว้ 512 MB

| ขั้น | ก่อนแก้ | หลังแก้ |
|:---|---:|---:|
| Python เปล่า | ~10 MB | ~10 MB |
| โหลดไลบรารีตัดคำ | 266 MB | 82 MB |
| โหลดดัชนี BM25 | 202 MB | 8 MB |
| โหลดตัวบท | 97 MB | 0.2 MB |
| โหลดเวกเตอร์ | 111 MB | ~56 MB |
| โมเดล embedding | ~1,400 MB | 0 MB (เรียกข้างนอก) |
| **รวมสูงสุด** | **519 MB ก่อนเริ่มเว็บเซิร์ฟเวอร์** | **227 MB** |
| เวลาบูต | ~30 วินาที | 0.7 วินาที |

**ตัวเลข 0.2 MB ของตัวบท** คือ 27,203 ตำแหน่งไบต์เก็บเป็น list ของ int
เทียบกับ 97 MB ถ้าแปลงทุกบรรทัดเป็น dict — เพราะหนึ่ง dict กลายเป็นออบเจกต์ Python
หกตัวบวกสตริงอีกชุด และแต่ละตัวมีค่าใช้จ่ายของตัวเอง

การอ่านใช้ตัวจัดการไฟล์เดียวร่วมกันพร้อมล็อก เพราะ webhook ตอบหลายเหตุการณ์พร้อมกัน
ถ้าไม่ล็อก คำขอหนึ่งจะอ่านจากตำแหน่งที่อีกคำขอเพิ่งเลื่อนไป

## 14. ตัวอย่างเดินครบวงจร

คำถาม `โดนไล่ออก ได้เงินไหม`

| ขั้น | สิ่งที่เกิด | ผลลัพธ์ |
|:---:|:---|:---|
| 1 | แปลงเลขไทยเป็นอารบิก | ไม่มีเลขไทย ข้อความเท่าเดิม |
| 2 | ตรวจคำทักทาย | ไม่ตรง ไปต่อ |
| 3 | ตรวจด่านที่ 1 | ไม่ตรงกลุ่มไหน ไปต่อ |
| 4 | เติมศัพท์กฎหมาย | `โดนไล่ออก ได้เงินไหม การเลิกจ้าง ค่าชดเชย` |
| 5 | แปลงเป็นเวกเตอร์ | เรียก Cloudflare ได้เวกเตอร์ 1,024 ตัว |
| 6 | คูณกับดัชนี 27,203 แถว | สูงสุด 0.6812 ที่ คุ้มครองแรงงาน ม.118 |
| 7 | ตัดคำแล้วคิดคะแนน BM25 | 7 โทเคน สูงสุด 22.415 ที่ ม.121 |
| 8 | รวมอันดับ + ที่นั่งสำรอง | ได้ 6 ชิ้นตามตารางข้อ 6.2 |
| 9 | ตรวจด่านที่ 2 | 0.6812 ≥ 0.54 ผ่าน |
| 10 | ส่งให้ Typhoon | ได้คำตอบพร้อมวงเล็บอ้างมาตรา |
| 11 | ตรวจด่านที่ 3 | ชื่อกฎหมายที่โมเดลอ้างอยู่ในชุดที่ส่งไป ผ่าน |
| 12 | กรองรูปแบบ | ตัดสัญลักษณ์ที่ LINE แสดงไม่ได้ |
| 13 | ประกอบคำตอบ | ข้อความ + การ์ด + คำเตือน |

**ขั้นที่ 6 กับ 7 บอกอะไร** สองฝั่งชี้ไปคนละมาตรา — dense ชี้ ม.118 ที่ระบุอัตราค่าชดเชย
BM25 ชี้ ม.121 ที่พูดถึงการเลิกจ้างเพราะปรับปรุงหน่วยงาน ทั้งคู่เกี่ยวข้อง
และการรวมอันดับทำให้ได้ทั้งสองมาตราติดไปด้วยกัน ซึ่งคือเหตุผลที่ต้องค้นสองทางตั้งแต่แรก

## 15. คำสั่งที่ใช้บ่อย

```bash
# สร้างข้อมูลและดัชนีใหม่ทั้งหมด
python -m ingest.extract_acts              # ~1 นาที
python -m ingest.build_index               # dense ~20-40 นาที

# ตรวจว่าระบบยังถูกต้อง
pytest tests -q                            # 150 เทสต์
python -m ingest.calibrate                 # เกณฑ์ปฏิเสธ
python -m ingest.eval_retrieval --n 400    # วัดการค้นคืนแบบเร็ว
python -m ingest.tune_fusion               # ไล่กริดหาน้ำหนัก

# รันในเครื่อง
uvicorn app.main:app --reload --port 8000

# รันแบบเดียวกับบนเซิร์ฟเวอร์
docker build -t thai-law-bot .
docker run --rm -p 8000:8000 --memory 512m --cpus 0.1 --env-file .env thai-law-bot

# ค้นอย่างเดียว ไม่เปลืองโควตาโมเดล
curl -sG http://localhost:8000/search --data-urlencode "q=ถูกเลิกจ้าง ได้ค่าชดเชยเท่าไหร่"
```

## 16. สิ่งที่ต้องรันใหม่เมื่อเปลี่ยนอะไร

| เปลี่ยนอะไร | ต้องรันใหม่ |
|:---|:---|
| แก้ `corpus.jsonl` | `build_index` ทั้งสองฝั่ง แล้ว `calibrate` แล้ว `eval_retrieval` |
| เปลี่ยนโมเดล embedding | `build_index --dense` แล้ว **`calibrate` บังคับ** เพราะเกณฑ์ 0.54 ผูกกับโมเดล |
| เปลี่ยนผู้ให้บริการ embedding | `test_embed_parity` **ก่อน** ชี้ระบบจริงไปที่นั่น |
| แก้ตารางเติมศัพท์ | `eval_retrieval` และ `tune_fusion` |
| แก้ตัวตัดคำ | `build_index --bm25` แล้ว `test_tokenizer_parity` |
| แก้กฎด่านที่ 1 | `calibrate` และ `test_smalltalk` (ตัวที่ไล่คำถามตัวอย่าง) |
| แก้น้ำหนักรวมอันดับ | `eval_retrieval` |
