# ผู้ช่วยกฎหมายไทย — ระบบนี้ทำงานอย่างไร

เอกสารอธิบายระบบถาม-ตอบกฎหมายไทยที่ตอบจากตัวบทพระราชบัญญัติจริง และอ้างเลขมาตราทุกคำตอบ

ใช้งานอยู่จริงที่ `https://thai-law-bot-c5zo.onrender.com` และผ่าน LINE
โค้ดทั้งหมดอยู่ที่ `github.com/NATX0XD/chatbot-thai-law`

ทุกตัวเลขในเอกสารนี้มาจากการวัดในระบบจริง วัดเมื่อ 30 สิงหาคม 2569
ท้ายเอกสารมีตารางบอกว่าตัวเลขแต่ละตัวมาจากคำสั่งไหน รันซ้ำได้ทุกตัว

เอกสารนี้เขียนให้คนที่ไม่ได้ทำงานสายนี้อ่านได้ ศัพท์เทคนิคทุกคำมีคำอธิบายกำกับ
ถ้าเจอคำที่ไม่คุ้น ดูที่หัวข้อ **คำศัพท์ที่โผล่บ่อย** ได้เลย

## คำศัพท์ที่โผล่บ่อย

อ่านผ่าน ๆ ก่อนก็ได้ แต่ละคำจะถูกอธิบายซ้ำอีกทีตอนที่ใช้จริง

| คำ | แปลว่าอะไรในเอกสารนี้ |
|:---|:---|
| **โมเดลภาษา** (LLM) | โปรแกรมที่เขียนข้อความต่อได้เหมือนคน เช่น ChatGPT ในระบบนี้ใช้ Typhoon ซึ่งเป็นโมเดลภาษาไทย |
| **RAG** | วิธีทำงานแบบ "ค้นเอกสารก่อน แล้วค่อยให้โมเดลสรุปเฉพาะที่ค้นได้" ย่อมาจาก Retrieval-Augmented Generation |
| **ค้นคืน** (retrieval) | ขั้นตอนหาว่ามาตราไหนในคลัง 26,658 มาตรา เกี่ยวกับคำถามนี้ |
| **ดัชนี** (index) | ตารางที่สร้างไว้ล่วงหน้าเพื่อให้ค้นเร็ว เหมือนดัชนีท้ายเล่มหนังสือ ต่างกันตรงที่ของเราสร้างด้วยเครื่อง |
| **เวกเตอร์** | ชุดตัวเลขที่ใช้แทนความหมายของข้อความ ระบบนี้ใช้ 1,024 ตัวเลขต่อหนึ่งข้อความ |
| **embedding** | การแปลงข้อความให้กลายเป็นเวกเตอร์ |
| **cosine** | ตัวเลข 0 ถึง 1 ที่บอกว่าสองข้อความความหมายใกล้กันแค่ไหน 1 = เหมือนกัน 0 = ไม่เกี่ยวกันเลย |
| **BM25** | สูตรให้คะแนนเอกสารจากการนับคำที่ตรงกับคำถาม มีมาก่อน AI นานมาก และยังใช้ได้ดี |
| **โทเคน** (token) | ชิ้นคำที่ตัดจากประโยค ภาษาไทยไม่เว้นวรรคระหว่างคำ จึงต้องมีโปรแกรมตัดคำให้ |
| **chunk** | ชิ้นข้อความที่ตัดจากมาตรายาว ๆ เพื่อให้ขนาดพอเหมาะกับการทำเวกเตอร์ |
| **prompt** | คำสั่งที่เราเขียนส่งไปให้โมเดลภาษาอ่านก่อนทำงาน |
| **hallucination** | อาการที่โมเดลภาษาแต่งข้อมูลขึ้นเองอย่างมั่นใจ ในงานกฎหมายคือแต่งเลขมาตรา |
| **API** | ช่องทางให้โปรแกรมคุยกับโปรแกรมอื่นข้ามเครื่อง |
| **webhook** | ช่องทางที่ LINE ใช้ส่งข้อความของผู้ใช้มาให้ระบบเรา |
| **คอนเทนเนอร์** (container) | กล่องที่ห่อโปรแกรมพร้อมของที่มันต้องใช้ทั้งหมด ยกไปรันที่ไหนก็ได้ผลเหมือนเดิม |

## ระบบนี้คืออะไร

แชตบอตที่ตอบคำถามกฎหมายไทยของคนทั่วไป โดยตอบจากตัวบทกฎหมายจริง 731 ฉบับ
และแนบเลขมาตราไว้ทุกคำตอบเพื่อให้ผู้ใช้เปิดไปตรวจเองได้

จุดที่ต่างจากแชตบอตทั่วไปมีข้อเดียว แต่เป็นข้อที่สำคัญที่สุด —
**ระบบนี้รู้ว่าตัวเองไม่รู้อะไร และบอกตรง ๆ แทนที่จะเดา**

---

## ปัญหาที่ตั้งใจแก้

คนทั่วไปมีคำถามกฎหมายในชีวิตประจำวันเต็มไปหมด ถูกเลิกจ้างได้เงินไหม
เจ้าหนี้โทรมาตอนตี 1 ผิดไหม บริษัทเอาข้อมูลเราไปใช้ได้แค่ไหน
แต่ช่องทางที่มีอยู่ตอบไม่ตรงจุด

| ช่องทางเดิม | ปัญหา |
|:---|:---|
| ค้นเว็บกฤษฎีกาเอง | ต้องรู้ก่อนว่ากฎหมายชื่ออะไร มาตราไหน ซึ่งคือสิ่งที่ผู้ถามยังไม่รู้ |
| ถามในเว็บบอร์ด | ได้ความเห็น ไม่ได้ตัวบท ตรวจสอบต่อไม่ได้ว่าใครพูดถูก |
| ปรึกษาทนาย | มีค่าใช้จ่าย และเกินความจำเป็นสำหรับคำถามเล็ก ๆ |
| ถามแชตบอตทั่วไป | ตอบลื่นไหลแต่แต่งเลขมาตราได้ และผู้ใช้แยกไม่ออกว่าอันไหนจริง |

**โจทย์จริงคือข้อสุดท้าย** โมเดลภาษาไม่ได้ตั้งใจโกหก มันแค่เขียนสิ่งที่ "น่าจะใช่"
ต่อจากคำถาม ซึ่งกับเรื่องทั่วไปก็พอใช้ได้ แต่กับกฎหมาย คำตอบที่ผิดแต่ฟังดูน่าเชื่อ
อันตรายกว่าการไม่ตอบ เพราะผู้ใช้เอาไปตัดสินใจต่อจริง ๆ

ระบบนี้จึงออกแบบให้ **ปฏิเสธเก่งกว่าตอบเก่ง**

## ตอบอะไรได้ ตอบอะไรไม่ได้

### ตอบได้

| รายการ | จำนวน |
|:---|---:|
| พระราชบัญญัติ / พระราชกำหนด (ฉบับล่าสุดของแต่ละฉบับ) | 731 ฉบับ |
| มาตราที่ทำดัชนีไว้ | 26,658 มาตรา |
| ชิ้นข้อความในดัชนี (มาตรายาวถูกตัดเป็นหลายชิ้น) | 27,203 ชิ้น |
| ข้อมูลปรับปรุงถึงประมาณ | พ.ศ. 2563 |

หมวดที่ครอบคลุมดีเป็นพิเศษ — แรงงาน, การทวงถามหนี้, ข้อมูลส่วนบุคคล,
ขายตรงและตลาดแบบตรง, จราจร

### ตอบไม่ได้ และบอกตรง ๆ ว่าไม่ได้

คลังข้อมูลต้นทางไม่มี **ประมวลกฎหมาย** เลยสักฉบับ

ประมวลกฎหมายกับพระราชบัญญัติต่างกันตรงนี้ — พระราชบัญญัติคือกฎหมายเฉพาะเรื่อง
ออกทีละฉบับตามความจำเป็น ส่วนประมวลกฎหมายคือกฎหมายพื้นฐานที่รวบรวมเรื่องใหญ่ ๆ
ไว้เป็นเล่มเดียว เช่นประมวลกฎหมายแพ่งและพาณิชย์ที่ว่าด้วยสัญญา หนี้ ครอบครัว มรดก

คลังนี้มีแต่แบบแรก ไม่มีแบบหลัง จึงตอบไม่ได้ในเรื่อง —
เช่าบ้าน มัดจำ กู้ยืม ค้ำประกัน ครอบครัว หย่า มรดก หมิ่นประมาท ฉ้อโกง ลักทรัพย์ ละเมิด

ข้อจำกัดนี้ไม่ได้ถูกซ่อน ระบบตรวจจับคำถามกลุ่มนี้แล้วบอกผู้ใช้ตรง ๆ ว่า
"เรื่องนี้อยู่ในประมวลกฎหมายแพ่งและพาณิชย์ บรรพ 6 ซึ่งคลังนี้ไม่มี"
พร้อมชี้ไปเว็บกฤษฎีกาและสายด่วนสภาทนายความ 1167

## ตัวอย่างคำตอบจริง

คำถาม: *ถูกเลิกจ้างกะทันหัน ได้ค่าชดเชยเท่าไหร่*

```
ถ้าถูกเลิกจ้างโดยไม่มีเหตุตามมาตรา 119 ให้ได้รับค่าชดเชยตามอายุงาน

• ทำงานครบ 120 วันแต่ไม่ครบ 1 ปี ได้ 30 วัน
• ครบ 1 ปีแต่ไม่ครบ 3 ปี ได้ 90 วัน
  ...
(พ.ร.บ.คุ้มครองแรงงาน 2541 ม.118)

ℹ️ ข้อมูลเบื้องต้นจากตัวบทกฎหมาย ไม่ใช่คำปรึกษาทางกฎหมาย ...
```

จุดสำคัญคือวงเล็บบรรทัดล่าง — **มีเลขมาตรากำกับ** ผู้ใช้เอาไปเปิดตัวบทตรวจเองได้
และเลขมาตรานั้นผ่านการตรวจแล้วว่ามาจากตัวบทที่ระบบค้นเจอจริง ไม่ใช่จากความจำของโมเดล

## ทำไมไม่ใช้แค่โมเดลภาษา

ระบบนี้ใช้วิธีที่เรียกว่า **RAG** แปลตรงตัวคือ "การสร้างคำตอบโดยมีการค้นคืนช่วย"
พูดง่าย ๆ คือ **ค้นเอกสารก่อน แล้วส่งเฉพาะเอกสารที่ค้นได้ให้โมเดลสรุป**

เปรียบเทียบให้เห็นภาพ — แทนที่จะถามคนที่อ่านกฎหมายผ่านตามาเมื่อสามปีก่อนแล้วให้ตอบจากความจำ
เราเดินไปหยิบตัวบทมาวางตรงหน้าเขาก่อน แล้วบอกว่า "สรุปให้ฟังหน่อย เอาเฉพาะที่อยู่ในกระดาษนี้"

| ทางเลือก | ทำไมไม่เลือก |
|:---|:---|
| ถามโมเดลภาษาเปล่า ๆ | โมเดลจำตัวบทไม่แม่น แต่งเลขมาตราได้ และตรวจย้อนไม่ได้ว่าเอามาจากไหน |
| ฝึกโมเดลใหม่ด้วยตัวบท (fine-tune) | ต้องฝึกใหม่ทุกครั้งที่กฎหมายแก้ ใช้ทรัพยากรสูง และยังไม่ได้แหล่งอ้างอิงกลับมาอยู่ดี |
| RAG | กฎหมายเปลี่ยน = สร้างดัชนีใหม่ ไม่ต้องแตะโมเดล และรู้เสมอว่าคำตอบมาจากมาตราไหน |

**หลักการสำคัญที่สุดของระบบนี้** โมเดลภาษาไม่มีหน้าที่ "รู้กฎหมาย"
มันมีหน้าที่ "เรียบเรียงตัวบทที่ระบบหามาให้ ให้คนทั่วไปอ่านรู้เรื่อง" เท่านั้น
ตัวที่ตัดสินว่าคำตอบมาจากไหน คือส่วนค้นคืน ไม่ใช่โมเดล

```

   │

   │
   ├─[1] กฎที่รู้ว่าคลังขาดอะไร        ─────────────> ปฏิเสธ + บอกว่าอยู่ในประมวลใด
   │      เรื่องนี้อยู่ในประมวลที่คลังไม่มีหรือเปล่า        (ไม่ค้น ไม่เรียกโมเดล)
   │
   ├─ เติมศัพท์กฎหมายให้คำถาม
   │
   ├─ ค้นคืนสองทางพร้อมกัน
   │      BM25   จับคำตรง เช่น "ค่าชดเชย" "มาตรา 118"
   │      Dense  จับความหมาย เช่น "โดนไล่ออกกะทันหัน"
   │      └─ รวมอันดับ + สำรองที่นั่งให้ตัวท็อปของแต่ละฝั่ง + ดันเลขมาตราที่ผู้ใช้ระบุ
   │
   ├─[2] คะแนนความใกล้เคียงสูงสุด < 0.54 ? ───────> ปฏิเสธ "ไม่พบตัวบทที่เกี่ยวข้อง"
   │                                                  (ไม่เรียกโมเดล)
   ├─ ส่ง 6 มาตราที่ได้ + คำถาม ให้โมเดลเรียบเรียง
   │
```

คือการถามคนที่กำลังจะเดา ว่ากำลังเดาอยู่หรือเปล่า

## การค้นคืนสองทาง

คำถามกฎหมายไทยมาสองแบบ และแต่ละแบบพังคนละวิธี

| แบบคำถาม | ตัวอย่าง | BM25 | Dense |
|:---|:---|:---|:---|
| ผู้ใช้รู้ศัพท์กฎหมาย | "ค่าชดเชย มาตรา 118" | เจอแม่น | มักพลาด เพราะโมเดลกลืนตัวเลข |
| ผู้ใช้พูดภาษาชาวบ้าน | "โดนไล่ออกกะทันหัน ได้เงินไหม" | **ไม่เจอเลย** | เจอ |

ที่ BM25 ไม่เจอเลยในแถวล่าง เพราะ **ไม่มีมาตราไหนในกฎหมายไทยเขียนคำว่า "ไล่ออก"**
ตัวบทเขียนว่า "การเลิกจ้าง"

ใช้ทางเดียวคือยอมพังกับคำถามครึ่งหนึ่งตั้งแต่ต้น จึงค้นทั้งสองทางแล้วรวมอันดับกัน
วิธีนี้เรียกว่า **hybrid**

### BM25 คืออะไร

สูตรให้คะแนนเอกสารจากการนับคำ แต่ฉลาดกว่าการนับเฉย ๆ สามข้อ

1. คำที่หายากมีน้ำหนักมากกว่าคำที่โผล่ทุกที่ — คำว่า "ค่าชดเชย" มีค่ากว่าคำว่า "การ"
2. เจอคำเดิม 10 ครั้ง ไม่ได้แปลว่าเกี่ยวข้องมากกว่าเจอ 5 ครั้งเป็นเท่าตัว คะแนนจึงอิ่มตัว
3. เอกสารยาวมีโอกาสมีคำตรงมากกว่าโดยบังเอิญ จึงถูกหักตามความยาว

ตัวเลขตั้งค่ามาตรฐาน k1 = 1.5 และ b = 0.75 (สองตัวนี้คุมข้อ 2 กับข้อ 3)
เอกสารในคลังยาวเฉลี่ย 91.11 โทเคน คลังคำมี 10,867 คำ
และตารางที่บอกว่าคำไหนอยู่ในเอกสารไหนบ้างมี 1,461,054 รายการ

**ก่อนจะนับคำได้ ต้องตัดคำก่อน** ภาษาไทยไม่เว้นวรรคระหว่างคำ คอมพิวเตอร์จึงไม่รู้ว่า
"ค่าชดเชยการเลิกจ้าง" ควรตัดตรงไหน ระบบใช้ตัวตัดคำชื่อ newmm ซึ่งเทียบกับคลังคำ 62,074 คำ
แล้วเลือกวิธีตัดที่ได้จำนวนคำน้อยที่สุด

### Dense คืออะไร

อีกทางหนึ่ง แทนที่จะนับคำ เราแปลง **ความหมาย** ของข้อความเป็นตัวเลข

โปรแกรมที่ทำหน้าที่นี้เรียกว่า embedding model ระบบนี้ใช้ตัวชื่อ BGE-M3
มันอ่านข้อความแล้วคายตัวเลขออกมา 1,024 ตัว ซึ่งเรียกรวมกันว่า **เวกเตอร์**

คิดว่าเป็นพิกัดบนแผนที่ก็ได้ ข้อความที่ความหมายใกล้กันจะได้พิกัดที่อยู่ใกล้กัน
ต่างกันตรงที่แผนที่จริงมี 2 แกน (เหนือ-ใต้ ออก-ตก) แต่แผนที่นี้มี 1,024 แกน

วิธีวัดว่าใกล้กันแค่ไหนเรียกว่า **cosine** ให้ค่าออกมาระหว่าง 0 ถึง 1
1 คือความหมายเหมือนกัน 0 คือไม่เกี่ยวกันเลย

เราแปลงทั้ง 27,203 ชิ้นข้อความเป็นเวกเตอร์เก็บไว้ล่วงหน้า
พอผู้ใช้ถามมา ก็แปลงคำถามเป็นเวกเตอร์แล้วเทียบกับทั้ง 27,203 ตัว หาตัวที่ใกล้ที่สุด

**ทำไม dense พลาดเลขมาตรา** เพราะโมเดลพวกนี้ถูกฝึกให้เข้าใจความหมาย
และ "มาตรา 118" กับ "มาตรา 119" ความหมายแทบเหมือนกันในสายตามัน — ทั้งคู่คือ "มาตราอะไรสักอย่าง"
ตรงนี้ BM25 ที่นับคำตรง ๆ ชนะขาด

---

## ทำไมไม่ใช้ vector database

เวกเตอร์ทั้งหมด 27,203 ตัว × 1,024 ตัวเลข เก็บแบบประหยัดที่ตัวเลขละ 2 ไบต์ = **55.7 MB**

ขนาดเท่านี้โหลดเข้าหน่วยความจำได้ทั้งก้อน แล้วคำนวณทีเดียวจบในหลักมิลลิวินาที

vector database (เช่น pgvector, Qdrant, Pinecone) เป็นระบบฐานข้อมูลเฉพาะทาง
สำหรับเก็บเวกเตอร์จำนวนมาก มันจำเป็นเมื่อเวกเตอร์เยอะจนโหลดเข้าเครื่องไม่ไหว
ที่ขนาดนี้การเพิ่มมันเข้ามาคือการเพิ่มระบบที่ต้องดูแลโดยไม่ได้อะไรกลับมา

**การเลือกไม่ใส่เครื่องมือ ก็เป็นการออกแบบ** และเกณฑ์ที่ใช้ตัดสินคือ
ดัชนีจะโตเกินหน่วยความจำเมื่อไหร่ — ถ้าเพิ่มประมวลกฎหมายทั้ง 6 ฉบับเข้ามา
ดัชนียังอยู่ราว 70–80 MB ยังไม่ถึงจุดที่ต้องเปลี่ยน

## ปัญหาจริงข้อ 1: ผู้ใช้พูดคนละภาษากับตัวบท

นี่คือสาเหตุการค้นพลาดอันดับหนึ่งของระบบ

ผู้ใช้พิมพ์ "โดนไล่ออก ได้เงินไหม" แต่ตัวบทเขียนว่า "การเลิกจ้าง" และ "ค่าชดเชย"

**วิธีแก้** ตารางคำ 35 กลุ่ม แปะศัพท์กฎหมายต่อท้ายคำถามก่อนเอาไปค้น
เช่นเจอคำว่า "ไล่ออก" ก็เติม "การเลิกจ้าง ค่าชดเชย" ต่อท้ายให้อัตโนมัติ

| คำถามเดิม | cosine ก่อน → หลัง | มาตราอันดับ 1 ก่อน → หลัง |
|:---|:---|:---|
| โดนไล่ออก ได้เงินไหม | 0.63 → 0.77 | พ.ร.บ.เงินเดือนข้าราชการ → คุ้มครองแรงงาน ม.118/119/122 |
| ลาพักร้อนกี่วัน | 0.61 → 0.78 | ม.41 → ม.30 |
| เจ้าหนี้ทวงหนี้ตี 1 ผิดไหม | 0.64 → 0.65 | บริษัทมหาชน ม.162 → ทวงถามหนี้ ม.9/11/12 |

แถวแรกเห็นชัดที่สุด — ก่อนเติมศัพท์ ระบบไปเจอกฎหมายเงินเดือนข้าราชการ
ซึ่งไม่เกี่ยวกับลูกจ้างบริษัทเลย

**ทำไมใช้ตารางแทนที่จะให้โมเดลช่วยเขียนคำถามใหม่** — ไม่มีค่าใช้จ่าย ไม่เพิ่มเวลารอ
ให้ผลเดิมทุกครั้ง และเขียนเทสต์ตรวจได้ ข้อเสียคือรู้จักเฉพาะคำที่อยู่ในตาราง
แต่คำที่ไม่อยู่ในตารางจะกลับไปใช้คำถามดิบ ซึ่งคือพฤติกรรมเดิมก่อนมีตารางนี้ —
**คำที่ขาดทำให้ผลแย่ลงได้ แต่ทำให้พังไม่ได้**

**ศัพท์ถูกเติม ไม่ใช่แทนที่** คำของผู้ใช้ยังอยู่ครบ เพื่อให้ BM25 ยังทำงานกับคำเดิมได้

## ปัญหาจริงข้อ 2: การรวมอันดับฝังคำตอบที่ถูกที่สุดไว้ท้ายแถว

เมื่อค้นสองทางแล้ว ต้องรวมผลเป็นอันดับเดียว ปัญหาคือคะแนน BM25
กับคะแนน cosine อยู่คนละสเกลโดยสิ้นเชิง เทียบกันตรง ๆ ไม่ได้

วิธีที่ใช้เรียกว่า **RRF** — ทิ้งคะแนนไปเลย ดูแต่ **อันดับ** แล้วให้แต้มตามสูตร
`น้ำหนัก / (60 + อันดับ)` ใครติดอันดับดีจากทั้งสองฝั่งก็ได้แต้มรวมสูง

เหมือนกรรมการสองคนให้คะแนนคนละเกณฑ์ เราจึงไม่เอาคะแนนดิบมาบวกกัน
แต่ดูว่าแต่ละคนจัดใครไว้อันดับเท่าไหร่แทน

**แต่มันมีจุดตายที่เจอกับคำถามจริง**

คำถาม "ถูกเลิกจ้างกะทันหัน ได้ค่าชดเชยเท่าไหร่"

| มาตรา | อันดับฝั่ง dense | อันดับฝั่ง BM25 | แต้มรวม |
|:---|:---|:---|:---|
| **ม.118** — มาตราที่ระบุอัตราค่าชดเชยจริง | อันดับ 1 (cosine 0.667) | ไม่ติด 30 อันดับแรก | 1/61 |
| ม.119–122 — มาตราข้างเคียง | กลางตาราง | กลางตาราง | ~1/31 + 1/31 |

มาตราที่ตอบคำถามได้ตรงที่สุด ได้แต้มจากฝั่งเดียว เลยแพ้มาตราที่กลาง ๆ ทั้งสองฝั่ง
ผลคือ **หลุด 10 อันดับแรก**

**วิธีแก้** สำรองที่นั่ง 2 ที่ให้ผลอันดับต้นของฝั่ง dense เสมอ ไม่ว่าแต้มรวมจะเป็นเท่าไหร่
ฝั่ง BM25 ไม่ได้ที่สำรอง เพราะวัดแล้วอันดับ 1 ของ BM25 กับคำถามภาษาพูดสั้น ๆ มักไม่เกี่ยวเลย

**น้ำหนักที่ใช้** dense 2.0 : BM25 0.5 เลือกจากการไล่ลองทุกค่าในกริดแล้ววัดกับคำถามที่รู้เฉลย
ปรับจาก 1:1 เป็น 2:1 ทำให้กฎหมายที่ถูกติด 3 อันดับแรกเพิ่มจาก 9/12 เป็น 11/12

## ปัญหาจริงข้อ 3: แต้มรวมใช้เป็นด่านกันไม่ได้เลย

ตอนแรกวางด่านไว้ว่า "ถ้าแต้มรวมต่ำกว่าเกณฑ์ให้ปฏิเสธ"

แต่สูตรรวมอันดับคิดจาก **อันดับล้วน** ไม่ได้คิดจากความใกล้ ผลคือ

| คำถาม | แต้มรวมสูงสุด |
|:---|:---|
| สูตรทำต้มยำกุ้งใส่อะไรบ้าง | 0.0164 |
| คำถามแรงงานที่ตรงเป๊ะ | 0.0164 |

**เท่ากันเป๊ะ** เพราะทั้งสองคำถามก็มี "อันดับ 1" ของตัวเองเสมอ
ต่อให้อันดับ 1 นั้นจะไม่เกี่ยวอะไรเลยก็ตาม ด่านนั้นจึงไม่มีผลอะไรมาตั้งแต่แรก

**ย้ายไปวัดที่ cosine ดิบ** ซึ่งมีขนาดจริง — 0.30 กับ 0.75 ต่างกันจริง
และ **ตัด BM25 ออกจากด่าน** เพราะวัดแล้วคำถามนอกเรื่องได้ BM25 สูงถึง 15.1
ขณะที่คำถามที่ตอบได้ต่ำสุดอยู่ที่ 12.6 คะแนน BM25 จึงไม่บอกอะไรเลยว่าคลังรู้เรื่องนี้ไหม
(สาเหตุคือคำถามยาว ๆ มีคำกฎหมายทั่วไปปนอยู่ ไปตรงกับมาตราอะไรก็ได้)

**บทเรียน** ตัววัดที่ใช้จัดอันดับได้ ไม่จำเป็นต้องใช้ตัดสิน "ตอบหรือไม่ตอบ" ได้

## ด่านที่ 1: กฎที่รู้ว่าคลังขาดอะไร

**ปัญหา** คำถามกฎหมายที่กฎหมายไม่อยู่ในคลัง คือกรณีที่อันตรายที่สุด
เพราะระบบค้นเจอกฎหมายจริงที่หัวข้อใกล้เคียง แล้วดูเหมือนค้นสำเร็จ

ตัวอย่าง "จดทะเบียนสมรสแล้วอยากหย่า ต้องทำยังไง"

→ ค้นเจอ **พ.ร.บ.จดทะเบียนครอบครัว** ที่ cosine 0.644
→ เป็นกฎหมายจริง หัวข้อตรงเป๊ะ แต่ **ไม่มีเหตุฟ้องหย่าอยู่ในนั้น**
   เพราะเหตุหย่าอยู่ในประมวลกฎหมายแพ่งและพาณิชย์ บรรพ 5 ซึ่งคลังไม่มี

ในสายตาระบบค้นคืน นี่คือการค้นที่สำเร็จ คะแนนแยกกรณีนี้ไม่ได้

**วิธีแก้** ใช้กฎเจาะจง 8 กลุ่ม ตรวจก่อนค้นเลย เพราะเรารู้แน่ชัดอยู่แล้วว่าคลังขาดประมวลใดบ้าง
เจอคำในกลุ่มไหนก็บอกผู้ใช้ไปตรง ๆ ว่าเรื่องนี้อยู่ในประมวลอะไร แล้วให้ไปดูที่ไหนต่อ

จับคำ **ภาษาที่คนใช้จริง** ไม่ใช่ศัพท์กฎหมาย — ผู้ใช้คนหนึ่งพิมพ์ "ขโมยของ" ไม่ใช่ "ลักทรัพย์"
กฎรุ่นแรกที่มีแต่ศัพท์กฎหมายจึงพลาด และนั่นทำให้เกิดเคสในหัวข้อด่านที่ 3

## ด่านที่ 2: เกณฑ์ที่มาจากการวัด ไม่ใช่การเดา

ด่านนี้ถามคำถามเดียว — คลังมีอะไรใกล้เคียงคำถามนี้บ้างไหม
ถ้าค่า cosine สูงสุดต่ำเกินไป แปลว่าไม่มี ก็ปฏิเสธไปเลยโดยไม่เรียกโมเดล

ค่าเกณฑ์ไม่ได้ตั้งจากความรู้สึก แต่มาจากการยิงคำถาม 3 กลุ่มผ่านระบบแล้วดูการกระจายคะแนน

| กลุ่มคำถาม | จำนวน | cosine สูงสุดที่วัดได้ |
|:---|---:|:---|
| ต้องตอบได้ | 14 ข้อ | 0.592 – 0.754 |
| ไม่ใช่คำถามกฎหมายเลย (สูตรอาหาร ผลบอล พยากรณ์อากาศ) | 5 ข้อ | 0.331 – 0.496 |
| เป็นคำถามกฎหมาย แต่ตัวบทไม่อยู่ในคลัง | 5 ข้อ | 0.521 – 0.659 |

- สองกลุ่มแรกแยกกันสะอาด มีช่องว่างระหว่าง 0.496 กับ 0.592 → **ตั้งเกณฑ์ที่ 0.54**
- กลุ่มที่สาม **ทับกับกลุ่มแรก** (0.659 สูงกว่า 0.592) → เกณฑ์คะแนนแยกกรณีนี้ไม่ได้ตลอดกาล
  จึงต้องมีด่านที่ 1 มาช่วย

**ข้อยกเว้นที่ตั้งใจ** ถ้าผู้ใช้พิมพ์เลขมาตรามาเอง เช่น "มาตรา 118 ว่าอย่างไร"
ให้ข้ามเกณฑ์ เพราะผู้ใช้บอกแล้วว่าต้องการตัวบทไหน และค่า cosine ต่ำไม่ได้แปลว่ามาตรานั้นไม่มี

## ด่านที่ 3: ตรวจคำตอบหลังโมเดลเขียนเสร็จ

**เคสจริงที่ทำให้ต้องมีด่านนี้**

ผู้ใช้ถามเรื่องเพื่อนขโมยของในร้าน ระบบไม่มีประมวลกฎหมายอาญาให้ค้น
จึงคืน **พ.ร.บ.ระบบการชำระเงิน มาตรา 48** ที่ cosine 0.588 — เหนือเกณฑ์ แต่ไม่เกี่ยวกันเลย

โมเดล **ไม่สนใจตัวบทที่ให้ไป** แล้วตอบจากความจำตัวเอง

```
"มีความผิดฐานลักทรัพย์ตามประมวลกฎหมายอาญา มาตรา 335 ... โทษจำคุกไม่เกิน 5 ปี
 (พ.ร.บ. ว่าด้วยการกระทำผิดเกี่ยวกับทรัพย์สิน พ.ศ. ...)"
```

- ประมวลกฎหมายอาญา **ไม่มีในคลัง**
- พ.ร.บ. ตัวที่สอง **ไม่มีอยู่จริงในโลก**

มั่นใจ เจาะจง และแต่งขึ้นทั้งหมด — เอาต์พุตที่แย่ที่สุดที่บอตกฎหมายจะให้ได้
อาการแบบนี้มีชื่อเรียกว่า hallucination

**คำสั่งใน prompt ห้ามไม่อยู่** และกฎจับคำก็ไล่คำว่า "ขโมย" ให้ครบทุกแบบไม่ได้
จึงต้องตรวจ **หลังบ้าน** — ทุกชื่อกฎหมายที่โผล่ในคำตอบ ต้องเป็นชื่อที่เราส่งให้โมเดลจริง
ถ้าไม่ใช่ ทิ้งคำตอบทั้งอัน แล้วบอกผู้ใช้ตรง ๆ ว่าตรวจสอบไม่ได้จึงไม่ส่งให้

**รายละเอียดที่เกือบพลาด** ชื่อกฎหมายปลอมชอบซ่อนต่อท้ายของจริง

```
"ตาม พ.ร.บ.การทวงถามหนี้ 2558 ม.9 และประมวลกฎหมายแพ่งและพาณิชย์"
```

ตัวตรวจรุ่นแรกอ่านทั้งก้อนเป็นชื่อเดียว แล้วปล่อยผ่านเพราะมันขึ้นต้นด้วยชื่อจริง
แก้โดยให้ตัดชื่อจบที่คำเชื่อม (และ, หรือ, ตาม, ซึ่ง)

## คำสั่งที่ให้โมเดล

ส่งไป 2 ส่วน — คำสั่งระบบ กับ คำถามผู้ใช้พร้อมตัวบท 6 มาตราที่ค้นได้

**ข้อบังคับด้านเนื้อหา**

1. ตอบจากตัวบทที่ให้มาเท่านั้น ห้ามใช้ความรู้อื่น
2. ทุกข้อความที่เป็นสาระทางกฎหมาย ต้องอ้างมาตราในวงเล็บ
3. ตัวบทไม่พอ ให้บอกตรง ๆ ห้ามเดา ห้ามแต่งเลขมาตรา
4. อธิบายด้วยภาษาคนทั่วไป ห้ามคัดตัวบทมาทั้งดุ้น
5. ตัวเลขสำคัญให้เขียนเป็นเลขอารบิก

**ข้อบังคับด้านรูปแบบ** เพราะ LINE แสดงข้อความธรรมดาเท่านั้น
ห้ามใช้สัญลักษณ์จัดรูปแบบอย่าง `**` หรือ `##` ห้ามวงเล็บเหลี่ยม
ห้ามใส่หัวข้อ "คำตอบ:" ห้ามทวนคำถาม ความยาวไม่เกิน 12 บรรทัด

**ยังต้องมีตัวกรองหลังบ้านอยู่ดี** เพราะโมเดล "ส่วนใหญ่" ทำตาม
และคำว่าส่วนใหญ่แปลว่าผู้ใช้บางคนจะเห็น `**` ดิบ ๆ ในแชต
prompt รุ่นแรกเคยใช้โครงในวงเล็บเหลี่ยม `[คำตอบสั้น 1-3 ประโยค]`
แล้วโมเดลลอกวงเล็บนั้นมาด้วยทั้งอัน

**ขั้นตอนจาก 42,755 ฉบับ เหลือ 731 ฉบับ**

1. เอาเฉพาะที่ขึ้นต้นด้วย พระราชบัญญัติ / พระราชกำหนด / ประมวล
2. ตัด พ.ร.บ. แก้ไขเพิ่มเติมทิ้ง — มันมีแต่รายการว่าแก้ตรงไหน ฉบับรวมมีเนื้อหาครบแล้ว
   ถ้าเก็บไว้จะได้ข้อความซ้ำที่อ้างเลขมาตราคนละความหมายมาแข่งกับฉบับจริง
3. ตัด พ.ร.บ. งบประมาณรายจ่ายประจำปี — เป็นตารางตัวเลข ไม่ตอบคำถามใคร
   และมาตราเดียวยาว 40,000 ตัวอักษร
4. คลังต้นทางเก็บ **หนึ่งแถวต่อหนึ่งฉบับปรับปรุง** ฉบับเดียวกันจึงโผล่หลายครั้ง
   → เลือกฉบับที่ต้นทางระบุว่าล่าสุด ถ้าไม่ระบุใช้ฉบับที่ยาวที่สุด
   (การแก้ไขมีแต่เพิ่มเนื้อหา ไม่เคยสั้นลง)
5. ตัดฉบับที่ N ที่มีฉบับรวมอยู่แล้ว แต่ **เก็บฉบับกำพร้าไว้** กรณีที่ไม่มีฉบับรวมเลย
6. ตัดแบ่งมาตรา — มาตราสั้นเก็บทั้งมาตรา มาตรายาวเกิน 1,800 ตัวอักษร
   ตัดเป็นชิ้นซ้อนกัน 200 ตัวอักษร (ซ้อนไว้เพื่อไม่ให้ประโยคที่ถูกตัดกลางหายไปจากทั้งสองชิ้น)

**เติมชื่อกฎหมายไว้หน้าทุกชิ้นก่อนแปลงเป็นเวกเตอร์** เพราะมาตราอย่าง
"ปีบัญชีของกองทุนหมายถึงปีงบประมาณ" อ่านเดี่ยว ๆ ไม่มีความหมายพอให้ค้นเจอ
แต่พอมีชื่อกฎหมายนำหน้า มันก็ยังตอบคำถามว่า "ปีบัญชีของกองทุน X คืออะไร" ได้

## หลักที่ใช้ตอนเปลี่ยนของ: ต้องพิสูจน์ว่าผลไม่เปลี่ยน

การเปลี่ยนของทั้ง 3 อย่างข้างบนมีความเสี่ยงเดียวกันหมด คือ **"พังเงียบ"**
ระบบยังทำงาน ไม่มีข้อความแจ้งข้อผิดพลาด แต่คำตอบแย่ลงโดยไม่มีใครรู้

|:---|:---|:---|
| ตัวคำนวณ BM25 | เทียบคะแนนกับตัวเดิม | ต่างกัน 0.0000026 (จากการปัดเลข) และอันดับ 30 อันดับแรกตรงกันทุกคำถาม |
| ตัวตัดคำ | เทียบผลตัดคำกับของเดิมบนตัวบทจริง 200 มาตราสุ่ม | ตรงกันทุกตัว |
| ผู้ให้บริการแปลงเวกเตอร์ | เทียบเวกเตอร์กับโมเดลที่รันในเครื่อง | cosine 0.999999 ทุกคำถาม และค้นได้มาตราชุดเดียวกัน |

ข้อสุดท้ายสำคัญที่สุด — ถ้าผู้ให้บริการเสิร์ฟโมเดลคนละตัว ค่า cosine จะเลื่อนทั้งระบบ

## การประเมินความถูกต้อง

### วัดอะไรบ้าง และทำไมต้องแยกวัด

แชตบอตแบบนี้ผิดได้ 3 จุด และ **วัดรวมกันไม่ได้** เพราะแก้คนละวิธี

| ระดับ | คำถามที่ต้องตอบ | ถ้าพัง อาการเป็นยังไง |
|:---|:---|:---|
| 1. ค้นคืน | ค้นเจอมาตราที่ตอบคำถามได้จริงไหม | คำตอบดูดี แต่อ้างมาตราที่ไม่เกี่ยว |
| 2. ด่านกัน | ปฏิเสธคำถามที่ควรปฏิเสธ และไม่ปฏิเสธคำถามที่ตอบได้ | เดามั่ว หรือปฏิเสธทั้งที่ตอบได้ |
| 3. เรียบเรียง | โมเดลสรุปตัวบทถูกต้องไหม | ตัวบทถูก แต่สรุปผิดความหมาย |

**วัดแล้ว** ระดับ 1 และ 2
**ยังไม่ได้วัด** ระดับ 3 — ต้องมีคนอ่านคำตอบเทียบตัวบททีละข้อ ซึ่งยังไม่ได้ทำ

### ชุดข้อมูลที่ใช้ประเมินการค้นคืน

ใช้ชุด WangchanX เพราะ **มีเฉลยระดับมาตรา** ไม่ใช่แค่คำตอบ
คือแต่ละคำถามมีคนบอกไว้แล้วว่าคำตอบอยู่ในกฎหมายฉบับไหน มาตราอะไร

| รายการ | จำนวน |
|:---|---:|
| คู่ถาม-ตอบทั้งหมด | 11,953 |
| ที่มีเฉลยระบุมาตรา | 11,881 |
| ที่เฉลยชี้ไปมาตราซึ่ง **มีอยู่จริงในคลังนี้** | **2,875** |

ที่เหลือ 9,006 คู่ เฉลยชี้ไปกฎหมายนอกคลัง ส่วนใหญ่คือประมวลกฎหมาย
เอามาวัดจะกลายเป็นการหักคะแนนตัวเองจากสิ่งที่ตั้งใจไม่มีตั้งแต่แรก

**วิธีวัด** ยิงคำถามทั้ง 2,875 ข้อผ่านระบบค้นคืนตัวจริง
แล้วดูว่ามาตราเฉลยโผล่ในผลลัพธ์อันดับที่เท่าไหร่

| ตัววัด | ความหมาย |
|:---|:---|
| hit@1 | มาตราเฉลยเป็นอันดับ 1 |
| hit@3 | มาตราเฉลยอยู่ใน 3 อันดับแรก |
| hit@6 | มาตราเฉลยอยู่ใน 6 อันดับแรก — สำคัญสุด เพราะระบบส่ง 6 มาตราให้โมเดล |
| MRR@6 | 1 หารด้วยอันดับที่เจอ เฉลี่ยทุกคำถาม เจอเร็ว = ค่าสูง เจอช้า = ค่าต่ำ |

### ผลการวัดการค้นคืน

วัดจากคำถาม 2,875 ข้อ ใช้เวลา 683 วินาที (0.24 วินาทีต่อข้อ)

| วิธีค้น | hit@1 | hit@3 | hit@6 | MRR@6 |
|:---|---:|---:|---:|---:|
| **ระบบจริง (ค้นสองทาง + รวมอันดับ + ที่นั่งสำรอง)** | **63.9%** | **79.8%** | **87.4%** | **0.725** |
| dense อย่างเดียว | 63.7% | 79.3% | 85.6% | 0.719 |
| BM25 อย่างเดียว | 49.2% | 64.2% | 72.0% | 0.574 |

**อ่านตัวเลขนี้ยังไง**

- **87.4%** ของคำถาม มาตราที่เป็นเฉลยอยู่ใน 6 มาตราที่ส่งให้โมเดล
  แปลว่าอีก **12.6%** โมเดลได้แต่ตัวบทที่ไม่มีคำตอบ
  และไม่มีทางตอบถูกได้เลยไม่ว่าโมเดลจะเก่งแค่ไหน
- **63.9%** เฉลยเป็นอันดับ 1 พอดี
- BM25 อย่างเดียวแพ้ชัดเจน ต่างกัน 15 จุดที่ hit@6

**สิ่งที่ต้องพูดตรง ๆ: การค้นสองทางชนะ dense อย่างเดียวแค่ 1.8 จุดที่ hit@6**

ไม่ใช่ตัวเลขที่น่าตื่นเต้น และมีคำอธิบายที่ต้องบอกด้วย —
ชุดคำถามนี้เขียนโดยผู้เชี่ยวชาญ จึงใช้ **ศัพท์กฎหมายที่ใกล้เคียงตัวบทอยู่แล้ว**
ซึ่งเป็นสนามที่ dense ถนัด และ **ไม่มีคำถามที่พิมพ์เลขมาตรามาเลย**
ซึ่งเป็นกรณีที่ BM25 ชนะขาด

ผู้ใช้จริงบน LINE พิมพ์ "โดนไล่ออก ได้เงินไหม" และ "ค่าชดเชย มาตรา 118"
ทั้งสองแบบไม่มีอยู่ในชุดประเมินนี้เลย ตัวเลข 1.8 จุด จึงเป็น **ค่าต่ำสุด**
ของประโยชน์ที่ BM25 ให้ ไม่ใช่ค่าจริง — และการจะได้ค่าจริง
ต้องมีชุดคำถามที่เขียนด้วยภาษาผู้ใช้จริง ซึ่งยังไม่มี

### ผลการวัดด่านกัน

ชุดคำถาม 24 ข้อ แยก 3 กลุ่มตามที่ควรจะเกิด

| กลุ่ม | จำนวน | ควรได้ | วัดได้ |
|:---|---:|:---|:---|
| คำถามที่คลังตอบได้ | 14 | ตอบทั้งหมด | **14/14** |
| คำถามที่ไม่ใช่กฎหมาย | 5 | ปฏิเสธทั้งหมด | **รั่ว 0/5** |
| คำถามกฎหมายที่ตัวบทไม่อยู่ในคลัง | 5 | ปฏิเสธทั้งหมด | **รั่ว 0/5** |

**ตัวเลขที่สำคัญกว่า: ปฏิเสธผิดบ่อยแค่ไหน**

วัดจากคำถาม 2,875 ข้อชุดเดียวกับหัวข้อก่อนหน้า ซึ่ง **พิสูจน์แล้วว่าคลังมีคำตอบ**
ถ้าด่านไหนปฏิเสธคำถามพวกนี้ คือปฏิเสธผิดแน่นอน

| ด่าน | ปฏิเสธผิด | สัดส่วน |
|:---|---:|---:|
| เกณฑ์ cosine ต่ำกว่า 0.54 | 6 ข้อ | 0.2% |
| กฎด่านที่ 1 (กฎที่รู้ว่าคลังขาดอะไร) | 52 ข้อ | 1.8% |

- เกณฑ์ cosine แทบไม่ปฏิเสธผิดเลย ค่า 0.54 จึงตั้งไว้พอเหมาะ
- **กฎด่านที่ 1 ปฏิเสธผิด 52 ข้อ** ซึ่งเป็นราคาที่จ่ายไปกับการใช้การจับคำ
  เช่นคำถามที่มีคำว่า "จำคุก" หรือ "อายุความ" จะถูกตีว่าเป็นเรื่องอาญาทันที
  ทั้งที่ พ.ร.บ. หลายฉบับก็มีบทกำหนดโทษจำคุกของตัวเอง

**นี่คือการแลกที่ตั้งใจ** ปฏิเสธผิด 1.8% แลกกับการไม่ตอบมั่วในเรื่องที่คลังไม่มีตัวบท
แต่ตอนนี้เรารู้ราคาแล้ว จากเดิมที่ไม่รู้

**ข้อควรระวังของชุด 24 ข้อ** ชุดนี้ **เขียนขึ้นเองระหว่างพัฒนา**
มันคือชุดที่ใช้ *เลือก* ค่า 0.54 การรายงานว่าผ่าน 14/14 บนชุดที่ใช้ตั้งค่าเอง
ไม่ใช่หลักฐานว่าระบบดี เป็นแค่หลักฐานว่าค่าที่ตั้งสอดคล้องกับชุดที่ใช้ตั้ง
ตัวเลขที่เชื่อได้มากกว่าคือ 2,875 ข้อซึ่งไม่ได้เขียนเอง

### ตัวอย่างที่ระบบยังผ่านด่านแต่ผิด

ระหว่างเตรียมเอกสารนี้ ทดสอบคำถามผู้บริโภคเพิ่ม แล้วเจอกรณีที่ด่านไม่จับ

| คำถาม | มาตราอันดับ 1 ที่ได้ | ผ่านด่านไหม |
|:---|:---|:---|
| สั่งของออนไลน์แล้วอยากคืนของ ทำได้ไหม | พ.ร.บ.**ชดเชยค่าภาษีอากรสินค้าส่งออก** ม.29 | ผ่าน ทั้งที่ไม่เกี่ยวเลย |
| ถูกหลอกขายของออนไลน์ ร้องเรียนที่ไหน | พ.ร.บ.**การทวงถามหนี้** ม.30 | ผ่าน ทั้งที่ไม่เกี่ยว |

**สาเหตุ** เกณฑ์ cosine ตอบได้แค่ "มีอะไรใกล้เคียงไหม"
ไม่ได้ตอบว่า "อันนี้ตอบคำถามได้จริงไหม" คำว่า "ส่งออก/สินค้า" กับ "ทวงถาม/ร้องเรียน"
ใกล้พอจะเกินเกณฑ์

**ผลกระทบจริง** ด่านที่ 3 จับไม่ได้ เพราะโมเดลอ้างกฎหมายที่เราส่งให้จริง ๆ
สิ่งที่กันไว้ได้เหลือแค่คำสั่งใน prompt ข้อ 3 ที่ให้บอกว่าข้อมูลไม่พอ
ซึ่งเป็นการกันที่อ่อนที่สุดในระบบ

**ทางแก้ที่ควรทำต่อ** ใส่ตัวจัดอันดับซ้ำแบบ cross-encoder — โปรแกรมที่อ่านคำถามกับมาตรา
**พร้อมกันทีเดียว** แล้วให้คะแนนว่าตอบกันได้ไหม ต่างจาก cosine ที่แปลงสองอย่างเป็นเวกเตอร์
แยกกันแล้วค่อยวัดระยะ วิธีแรกตอบคำถามว่า "ตอบได้จริงไหม" ได้ตรงกว่า แต่ช้ากว่า

### ข้อบกพร่องที่เจอจากการทดสอบหน้าจอ

ทดสอบด้วยการกดจริงบนเบราว์เซอร์ ไม่ใช่การอ่านโค้ด แล้วเจอ 2 อย่าง

**1. ปุ่มที่ดูเหมือนทำงานแต่ไม่ได้ทำ** เมนู "ตัวอย่างคำถาม" เรียกฟังก์ชันเดียวกับ "แชทใหม่"
และเมนู "คลังกฎหมายที่มี" พิมพ์ข้อความที่เขียนตายตัวไว้ ไม่ได้อ่านจากระบบจริง
แก้โดยเพิ่มช่องทางให้หน้าเว็บถามระบบว่าคลังมีอะไรบ้าง
แล้วให้หน้าจอแสดงเลขที่นับได้จริง (731 ฉบับ / 26,658 มาตรา)

**2. คำถามตัวอย่างที่บอตปฏิเสธเอง** รายการ "ตัวอย่างคำถาม" มีหมวดคอมพิวเตอร์ 3 ข้อ
ทดสอบจริงแล้ว 2 ข้อถูกปฏิเสธ — "แฮกเข้าระบบคนอื่นมีโทษอะไร" ติดกฎด่านที่ 1
เพราะคลังไม่มี พ.ร.บ.คอมพิวเตอร์ และ "เอารูปคนอื่นไปตัดต่อผิดไหม" ตกเกณฑ์ cosine
ตัดหมวดนั้นทิ้ง แทนด้วยหมวดผู้บริโภค และเพิ่มเทสต์ที่ไล่ทุกคำถามในรายการว่าไม่ตกด่านที่ 1

**บทเรียน** รายการตัวอย่างที่ผู้ใช้กดแล้วโดนปฏิเสธ แย่กว่าไม่มีรายการตัวอย่างเลย
เพราะมันเป็นคำสัญญาที่ระบบทำไม่ได้ และเป็นสิ่งแรกที่ผู้ใช้ใหม่กด

## ข้อจำกัดที่รู้ตัว

**เรื่องข้อมูล**

1. ไม่มีประมวลกฎหมายเลยสักฉบับ ทำให้คำถามที่คนถามบ่อยที่สุดหลายหมวดตอบไม่ได้
2. ข้อมูลหยุดที่ราว พ.ศ. 2563 กฎหมายที่แก้หลังจากนั้นจะได้ฉบับเก่า
3. ยังมีฉบับซ้ำจากชื่อสะกดต่างกันหลงเหลืออยู่

**เรื่องระบบ**

4. **ยังไม่ได้วัดความถูกต้องของคำตอบที่โมเดลเรียบเรียง** วัดแค่ว่าค้นเจอมาตราที่ถูกไหม
   การจะวัดต้องมีคนอ่านคำตอบเทียบตัวบททีละข้อ ซึ่งยังไม่ได้ทำ
5. กฎด่านที่ 1 เป็นการจับคำ พลาดได้ทั้งสองทาง — วัดแล้วปฏิเสธเกิน 1.8%
   ส่วนอัตราที่ปล่อยผ่านทั้งที่ควรปฏิเสธยังไม่ได้วัด
6. ยังไม่มีตัวจัดอันดับซ้ำ กรณี "ผ่านด่านแต่ผิด" จึงยังเกิดได้
7. ตอบทีละคำถาม ไม่จำบทสนทนาก่อนหน้า ถามต่อว่า "แล้วถ้าทำงาน 5 ปีล่ะ" จะไม่รู้เรื่อง
8. ยังไม่ได้วัดเวลาตอบตอนมีผู้ใช้จำนวนมากพร้อมกัน ทดสอบเดี่ยวอย่างเดียว
9. **พึ่งบริการภายนอกที่ไม่รับประกันความต่อเนื่อง** ทั้ง Typhoon และ Cloudflare เป็นของฟรี
   ฝั่ง Typhoon ผู้พัฒนาระบุเองว่าเป็นบริการเชิงวิจัย จำกัดอัตราเรียก และไม่เหมาะกับงานโหลดสูง
   ระบบมีทางถอยระดับหนึ่ง — โมเดลสำรองเมื่อตัวหลักตอบ 429 และถ้าพังทั้งคู่จะคืนตัวบทดิบให้แทน
   แต่ถ้าบริการปิดจริงต้องย้ายผู้ให้บริการ ซึ่งทำได้เพราะใช้โปรโตคอลกลาง

## สรุป

1. **ปัญหา** ข้อมูลกฎหมายผิดที่ฟังดูน่าเชื่อ อันตรายกว่าการไม่ตอบ
2. **วิธี** ค้นตัวบทจริงก่อน แล้วให้โมเดลเรียบเรียงเฉพาะสิ่งที่ค้นได้ พร้อมอ้างมาตราทุกครั้ง
3. **หลัก** ค้นสองทางเพราะคำถามมาสองแบบ และมีด่านกัน 3 ชั้น
   ที่ไม่มีชั้นไหนให้โมเดลตัดสินตัวเอง
4. **วัด** ค้นคืนวัดจาก 2,875 คำถามที่มีเฉลยระดับมาตรา ได้ hit@6 87.4%
   ปฏิเสธผิด 0.2% กับ 1.8% ส่วนความถูกต้องของคำตอบยังไม่ได้วัด และบอกตรง ๆ ว่ายังไม่ได้วัด
5. **สถานะ** ใช้งานได้จริงบน LINE และเว็บ ค่าใช้จ่าย 0 บาทต่อเดือน หน่วยความจำ 227 MB

## หัวข้อที่ยังไม่ได้เขียน และคิดว่าควรมี

เรียงตามที่คิดว่าจำเป็นก่อน

**1. จริยธรรมและความรับผิด** — จำเป็นที่สุด
ควรพูดว่าการให้ข้อมูลกฎหมายต่างจากการให้คำปรึกษาทางกฎหมายอย่างไร เส้นแบ่งอยู่ตรงไหน
ระบบวางตัวเป็น "ผู้ชี้ตัวบท" ไม่ใช่ "ผู้ให้ความเห็น" ซึ่งสะท้อนในคำสั่งข้อ 1
และคำเตือนท้ายทุกคำตอบ และถ้าผู้ใช้เอาไปใช้แล้วเสียหาย ใครรับผิด

**2. ข้อมูลส่วนบุคคลของตัวบอตเอง**
บอตที่ตอบเรื่อง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล ควรตอบได้ว่าตัวเองทำตามไหม
ตอนนี้ระบบบันทึกคำถามช่วง 80 ตัวอักษรแรกลงล็อกและไม่ได้เก็บรหัสผู้ใช้
ข้อความผู้ใช้ถูกส่งออกไป 2 ที่ — Cloudflare เพื่อทำเวกเตอร์ และ Typhoon เพื่อเรียบเรียง
ถ้าจะเก็บบันทึกคำถามจริงเพื่อพัฒนาต่อ ต้องขอความยินยอมและมีนโยบายก่อน

**3. เทียบกับการถามโมเดลเปล่า ๆ**
หยิบคำถามเดียวกันวางเทียบกัน ควรเลือกคำถามในคลัง 1 ข้อ และนอกคลัง 1 ข้อ (เช่นมรดก)
เพราะข้อหลังคือจุดที่ความต่างชัดที่สุด — ฝั่งหนึ่งเดา อีกฝั่งบอกว่าไม่มีข้อมูล

**4. งานที่เกี่ยวข้อง** ถ้าเป็นปริญญานิพนธ์
ระบบถาม-ตอบกฎหมายไทยที่มีคนทำไว้แล้วต่างจากงานนี้ตรงไหน และที่มาของ BM25 กับ RRF

**5. ไทม์ไลน์และการแบ่งงาน** ถ้าเป็นงานส่งวิชา
รวมถึงจุดที่เสียเวลามากที่สุดและเพราะอะไร

**6. แผนภาพสถาปัตยกรรมแบบภาพ**
แผนภาพในหัวข้อภาพรวมเป็นข้อความ ถ้าทำเป็นภาพจะอ่านง่ายกว่ามาก

**7. ความปลอดภัย**
ตรวจลายเซ็นทุกข้อความขาเข้า, คีย์ทั้งหมดอยู่ในตัวแปรสภาพแวดล้อมและไม่มีคีย์ใน git
(ตรวจย้อนทุกครั้งที่บันทึกโค้ดแล้ว), ข้อความผู้ใช้ไม่ถูกเอาไปประกอบเป็นคำสั่งใด ๆ
นอกจากส่งให้โมเดลอ่าน
