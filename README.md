# ผู้ช่วยกฎหมายไทย (KMUTNB Thai Law Chatbot)

แชตบอตถาม-ตอบกฎหมายไทย ตอบจากตัวบทพระราชบัญญัติจริงและอ้างเลขมาตราทุกคำตอบ
ต่อกับ LINE ได้ และมีหน้าเว็บไว้ทดสอบก่อนมี LINE channel

สร้างจากผลการสำรวจใน `report/รายงานชุดข้อมูลกฎหมายไทย.md` (106 หน้า)

## โครงสร้างโปรเจกต์

```
thai-law-bot/
├── data/
│   ├── raw/          ต้นฉบับที่ดาวน์โหลด ห้ามแก้ (382 MB)
│   ├── processed/    ชุดข้อมูลที่เอาไปใช้จริง (110 MB) ← ผลงานอยู่ตรงนี้
│   └── index/        ดัชนีค้นคืน สร้างใหม่ได้ ลบได้ (83 MB)
├── app/              ตัวแชตบอต (retriever, LLM, LINE, API)
├── ingest/           สคริปต์แปลง raw -> processed -> index
├── report/           รายงาน 106 หน้า + สคริปต์ที่สร้างมัน
├── tests/            45 เทสต์
└── web/              หน้าเว็บทดสอบ
```

รายละเอียดทุก field ของทุกไฟล์อยู่ใน [`data/README.md`](data/README.md)

## ข้อมูลที่ใช้

| รายการ | ค่า |
|:---|---:|
| พระราชบัญญัติ/พระราชกำหนด (ฉบับล่าสุดของแต่ละฉบับ) | 731 |
| มาตราที่ทำดัชนี | 27,218 |
| แหล่งข้อมูล | `pythainlp/thailaw` ผ่านฉบับทำความสะอาดของ `iapp/rag_thai_laws` (CC0) |
| ข้อมูลปรับปรุงถึง | ประมาณ พ.ศ. 2563 |

**ข้อจำกัดที่ต้องรู้ก่อนใช้** คลังต้นทางไม่มีประมวลกฎหมายแพ่งและพาณิชย์ ประมวลกฎหมายอาญา
และประมวลกฎหมายวิธีพิจารณาความ คำถามเรื่องเช่าบ้าน มัดจำ กู้ยืม ค้ำประกัน ครอบครัว มรดก
หมิ่นประมาท ฉ้อโกง จึงตอบไม่ได้ ระบบถูกออกแบบให้ **ปฏิเสธตรง ๆ** ในกรณีเหล่านี้แทนที่จะเดา
(ที่มาของช่องว่างนี้อยู่ในบทที่ 5 ของรายงาน)

## สถาปัตยกรรม

```
คำถาม
  │
  ├─ ชั้นที่ 1  coverage rule ── ตรงกับหมวดที่คลังไม่มี? ─> ปฏิเสธ บอกว่าอยู่ในประมวลใด
  │                              (ไม่เรียกทั้ง retrieval และ LLM)
  ├─ BM25 (pythainlp newmm)  ── จับคำตรง เช่น "ค่าชดเชย" "มาตรา 118"
  ├─ Dense (BGE-M3)          ── จับภาษาพูด เช่น "โดนไล่ออกกะทันหัน"
  │     └─ รวมอันดับด้วย RRF + สำรองที่นั่งให้ตัวท็อปของแต่ละฝั่ง + boost เลขมาตรา
  │
  ├─ ชั้นที่ 2  cosine สูงสุด < MIN_DENSE_SIM ─> ตอบ "ไม่ทราบ" ไม่เรียก LLM
  └─ ผ่านทั้งสองชั้น ─> Typhoon สรุป + อ้างมาตรา + disclaimer
```

### ทำไมต้องมี guard สองชั้น

วัดจริงด้วย `ingest/calibrate.py` แล้วได้ผลนี้

| กลุ่มคำถาม | cosine สูงสุด |
|:---|:---|
| ตอบได้ | 0.592 – 0.754 |
| ไม่ใช่คำถามกฎหมาย | 0.331 – 0.496 |
| เป็นคำถามกฎหมาย แต่ตัวบทไม่อยู่ในคลัง | 0.521 – 0.659 |

สองกลุ่มแรกแยกกันได้สะอาดที่ 0.54 แต่กลุ่มที่สาม **ทับกับกลุ่มแรก** และนี่คือกลุ่มที่อันตรายที่สุด
เช่น "จดทะเบียนสมรสแล้วอยากหย่า" ค้นเจอ พ.ร.บ.จดทะเบียนครอบครัว ที่ cosine 0.644 ซึ่งเป็น
กฎหมายจริงและตรงหัวข้อ แต่ไม่มีเหตุฟ้องหย่าอยู่ในนั้น เพราะเหตุหย่าอยู่ใน ป.พ.พ. บรรพ 5
ที่คลังไม่มี ในสายตาของ retriever นี่คือการค้นที่สำเร็จ

คะแนนจึงแยกกรณีนี้ไม่ได้ตลอดกาล ทางออกคือใช้กฎเจาะจงใน `app/coverage.py` เพราะเรารู้แน่ชัด
อยู่แล้วว่าคลังขาดประมวลใดบ้าง และการบอกผู้ใช้ว่า "เรื่องนี้อยู่ใน ป.พ.พ. บรรพ 6 ซึ่งระบบไม่มี"
มีประโยชน์กว่าการปฏิเสธลอย ๆ

**ทำไมต้อง hybrid** คำถามกฎหมายไทยมาสองแบบ ผู้ใช้ที่รู้ศัพท์พิมพ์ "ค่าชดเชย มาตรา 118"
ซึ่ง BM25 จับได้แม่นแต่ dense มักพลาดเพราะโมเดล embedding กลืนตัวเลข ส่วนผู้ใช้ทั่วไปพิมพ์
"โดนไล่ออกกะทันหัน ได้เงินไหม" ซึ่ง dense จับได้แต่ BM25 ไม่เจอเลย เพราะไม่มีมาตราไหน
เขียนคำว่า "ไล่ออก"

**ทำไมไม่ใช้ vector database** 27,218 เวกเตอร์ × 1024 มิติ แบบ float16 = 56 MB
โหลดเข้าหน่วยความจำแล้วคูณเมทริกซ์ครั้งเดียวก็ค้นเสร็จในหลักมิลลิวินาที
การเพิ่ม pgvector หรือ Qdrant ที่ขนาดนี้คือความซับซ้อนที่ไม่ได้อะไรกลับมา

## ติดตั้ง

ต้องมี Python 3.11 ขึ้นไป (torch ≥ 2.6 ไม่รองรับ 3.9)

```bash
cd thai-law-bot
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env          # แล้วใส่คีย์
```

### สร้างดัชนี

```bash
.venv/bin/python -m ingest.extract_acts    # data/raw -> data/processed/corpus.jsonl  (~1 นาที)
.venv/bin/python -m ingest.build_index     # data/processed -> data/index             (dense ~20-40 นาที)
```

ถ้า `data/raw/` หายไป ให้ดาวน์โหลดใหม่จาก `huggingface.co/datasets/iapp/rag_thai_laws`
และ `huggingface.co/datasets/airesearch/WangchanX-Legal-ThaiCCL-RAG`

### รัน

```bash
.venv/bin/uvicorn app.main:app --reload --port 8000
```

เปิด http://localhost:8000 เพื่อทดสอบผ่านหน้าเว็บ

## ต่อกับ LINE

ยังไม่ต้องมี channel ก็รันได้ ระบบจะปิดเฉพาะส่วน `/webhook` ไว้ เมื่อพร้อมแล้วทำตามนี้

1. สร้าง Provider และ **Messaging API channel** ที่ https://developers.line.biz/console/
2. คัดลอกค่าลง `.env`
   - `LINE_CHANNEL_SECRET` — แท็บ *Basic settings*
   - `LINE_CHANNEL_ACCESS_TOKEN` — แท็บ *Messaging API* กด issue แบบ long-lived
3. เปิดพอร์ตออกอินเทอร์เน็ต ตอนพัฒนาใช้ `ngrok http 8000` หรือ `cloudflared tunnel --url http://localhost:8000`
4. ในแท็บ *Messaging API* ตั้ง **Webhook URL** เป็น `https://<โดเมนของคุณ>/webhook` แล้วกด Verify
5. เปิด *Use webhook* และ **ปิด** *Auto-reply messages* กับ *Greeting messages*
   ไม่งั้น LINE จะตอบข้อความอัตโนมัติทับคำตอบของบอต

### ข้อจำกัดเรื่องเวลาที่ต้องรู้

LINE คาดหวังให้ webhook ตอบ 200 ภายในไม่กี่วินาที และ reply token หมดอายุราว 30 วินาที
แต่ RAG + Typhoon ใช้เวลานานกว่านั้นได้ โค้ดจึงตอบ 200 ทันทีแล้วประมวลผลใน background task
ถ้า reply token หมดอายุก่อนจะสลับไปใช้ push API ให้เอง

## สิ่งที่ยังไม่ได้ทำ

- **ประมวลกฎหมาย** ต้อง scrape เพิ่มจาก krisdika.go.th หมวดประมวลกฎหมาย (6 ฉบับหลัก)
  เป็นงานที่คุ้มที่สุดถ้าจะขยายต่อ เพราะปลดล็อกหมวดคำถามที่คนถามมากที่สุด
- **Reranker** ตอนนี้ใช้ RRF ล้วน การเพิ่ม cross-encoder จะแม่นขึ้นแต่ช้าลง
- **ชุดประเมิน** ยังไม่มีชุดคำถามจริงพร้อมเฉลยมาตรา รายงานเสนอไว้ที่ 200 ข้อสำหรับหมวดแรงงาน
- **จำบทสนทนา** ตอนนี้ตอบทีละคำถาม ไม่จำบริบทก่อนหน้า
- **ยังไม่ได้วัดเวลาตอบใต้โหลดจริง** ทดสอบเดี่ยวได้ 2–15 วินาที ขึ้นกับความยาวคำตอบของ Typhoon
- **coverage rule ยังเป็น keyword** `app/coverage.py` ใช้การจับคำ ซึ่งพลาดได้ทั้งสองทาง
  ควรมีชุดคำถามจริงมาวัดอัตราปฏิเสธผิดก่อนเปิดใช้งานกับคนหมู่มาก

## บันทึกปัญหาที่เจอระหว่างสร้าง

เก็บไว้เพราะทั้งสามข้อไม่มีอาการฟ้อง ระบบทำงานได้ปกติแต่ให้ผลผิด

**1. BGE-M3 บน MPS ให้เวกเตอร์ผิดเมื่อ encode ทีละข้อความ**
cosine เทียบกับผลบน CPU เหลือ 0.30 ในบางคำถาม แต่ถ้า encode เป็น batch ได้ 1.0000 พอดี
ดัชนีจึงไม่เสีย (สร้างด้วย batch 16) แต่ตอน query พังเงียบ ๆ ทำให้ "นายจ้างหักเงินเดือนได้ไหม"
ได้ cosine 0.2530 และค้นไปเจอ พ.ร.บ.การรับขนคนโดยสาร แก้โดยบังคับ encode query บน CPU
ตรวจซ้ำด้วยการสุ่ม 300 chunk มาเทียบกับ CPU แล้วได้ cosine 1.0000 ทุกตัว

**2. RRF ฝัง "คำตอบที่ถูกที่สุด" ไว้ท้ายแถว**
"ถูกเลิกจ้างกะทันหัน ได้ค่าชดเชยเท่าไหร่" มี ม.118 เป็นอันดับ 1 ฝั่ง dense (0.667) แต่ BM25
ไม่ติด top-30 จึงได้แต้ม 1/61 ส่วน ม.119-122 ที่กลาง ๆ ทั้งสองฝั่งได้ราว 1/31+1/31 แล้วแซงขึ้นไป
ผลคือมาตราที่ระบุอัตราค่าชดเชยจริงหลุด top-10 แก้โดยสำรองที่นั่งให้ผลอันดับต้นของแต่ละฝั่ง

**3. คะแนน RRF ใช้เป็น guardrail ไม่ได้เลย**
RRF คิดจากอันดับล้วน "สูตรทำต้มยำกุ้ง" จึงได้คะแนนสูงสุด 0.0164 เท่ากับคำถามแรงงานที่ตรงเป๊ะ
guard เดิมที่ตั้งบน RRF จึงไม่มีผลใด ๆ ย้ายไปวัดที่ cosine ดิบแทน และตัด BM25 ออกจาก guard
เพราะวัดแล้วพบว่าคำถามนอกเรื่องได้ BM25 สูงถึง 15.1 ขณะที่คำถามที่ตอบได้ต่ำสุดอยู่ที่ 12.6
